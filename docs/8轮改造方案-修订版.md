## 1. 决策定案（原方案留白的 7 项）

### D1 · 单一来源规则

| 概念 | 唯一权威来源 | 说明 |
|---|---|---|
| 目标考试类型 | `LearningGoal.examType` | **`StudyPlan.examType` 删除**（现在 `LongTermPlan.ets:124` 把 goal 的 exam 复刻进 plan，是纯双写） |
| 考试日期 | `LearningGoal.targetDate` | 不变 |
| **科目清单** | `LearningGoal.subjects` | **唯一**。StudyPlan 只存"科目 → 目标分钟"的**映射**，键必须取自 `subjects`；不允许在 StudyPlan 里新增科目 |
| 每科目标时长 | `StudyPlan.subjectTargets[].targetMinutes` | 用户手工维护 |
| 计划名 / 周期 | `StudyPlan.title` / `periodStart` / `periodEnd` | `periodEnd` 默认取 `goal.targetDate`（派生，用户可覆盖） |
| 任务归属 | `Task.planId` | 见 D2 |

> 为什么必须写死这条：原方案选了"不物理合表"，代价就是会出现**共享概念**。不留单一来源规则，新增的"科目"会比现在的 `examType` 双写更危险——`subjects` 决定 AI 规划背景与复盘目标行，"科目目标"决定进度分母，两者一旦漂移，进度和规划说的就是两件事。

### D2 · 本期任务集的生命周期

- `Task` 新增 `planId: string`（`''` = 自由专注 / 未归属，**不计入目标进度**）。
- 规划确认（`TaskPlanning.confirmStart` → `AppStore.persistPlan()`）时统一写 `planId = StudyPlan.PLAN_SINGLETON_ID`。
- **进度分母的任务集** = `tasks.filter(t => t.planId === 当前计划 id)`，按 `id` 去重。
- **跨天不失效**：任务一旦归属本期就一直算（完成即冻结在集合里），不因跨天而消失。这与"今日任务"（走 `currentPlan`）是两个口径，UI 文案必须区分。
- 未归属的 `''` 任务：只计入"实际投入"和条数统计，**不进百分比**。

### D3 · 总时长与分科之和的关系

**`totalEstimatedMinutes` 改为派生、只读** = `Σ subjectTargets[].targetMinutes`。

- UI 上显示为"合计"，不可直接编辑。
- 若用户只想填总数：提供**一键"按现有任务预计时长比例分摊到各科"**，分摊结果仍落到分科上。
- 原方案的"总和不一致时给校验"由此变成不可能发生（没有两个可编辑的真值）。若坚持两者可独立编辑，则必须明确"进度只用分科"，否则就是自找不一致。

### D4 · 旧数据迁移

- 判定旧记录：`subject_targets` 为空 **且** `total_estimated_minutes > 0`。
- 迁移动作：保留旧总值作为**"未分配目标"**，分科留空；UI 显示"已设总目标 120 小时，但还没分到科目 —— 进度暂时无法计算"，并给两个出口：**① 手动填各科** / **② 一键按现有任务预计时长比例分摊**。
- **不静默分摊**（与"避免静默修正"原则一致），但也不能让老用户卡死 —— 所以给一键入口，用户点了才分摊。
- 迁移**一次性、幂等**：读旧记录 → 以固定 id 写回新结构 → 后续不再判定。
- 历史多余行：`study_plan` 表可能有 N 行（见 §2.4）。迁移时取 `updated_at` 最新的一行作为权威，重写为固定 id；**其余行保留不删**（不引入不可逆操作），后续可加一次清理。

### D5 · 进度的主口径

**双口径并列，但主口径 = 实际投入，不是勾选完成。**

| 口径 | 公式 | 性质 |
|---|---|---|
| A 勾选完成（辅） | `Σ 已勾选任务.estimatedDuration ÷ Σ 各科目标分钟` | 由用户手动打钩驱动，不产生新信息 |
| **B 实际投入（主）** | `Σ 任务.actualDuration ÷ Σ 各科目标分钟` | 由会话计时自动产生，**不需要用户打钩** |

理由：用户抱怨的是"这个进度没有依据"。口径 A 只是把单位从**条数**换成**分钟**，语义没变，仍解决不了；口径 B 才是"这段目标时间里真的投进去了多少"。

- 前置：必须先做 §3 的 `actualDuration` 写回，否则口径 B 恒为 0。
- 口径 B 的字段注释要写明口径：**墙钟段长**（含该段内的休息/暂停，不细分）。

### D6 · 超额行为

- 进度条仍 `clamp(0,100)`；
- **主数值不 clamp**，显示 `实际投入 / 目标`（如 `135 / 120 分钟`），并加标签"已超出 15 分钟"；
- 同时给一句一键操作："要不要把目标上调到 135 分钟？"
- 这样超额既不会"粘在 100% 失去区分度"，也不丢信息。

### D7 · 样本门槛（必须量化）

| 用途 | 门槛 |
|---|---|
| 开始算"长期建议" | `profile.sampleCount ≥ 3`（沿用现有） |
| 单日**与基线比较** | 基线窗口内 **≥ 3 次会话** 且 **累计总学习 ≥ 60 分钟**；不足则 `ready=false`，只给当天事实 + "还差 N 次会话" |
| 基线窗口选择 | 优先近 **7** 天；不达门槛扩到近 **30** 天；仍不达则不给对比 |
| 基线是否含当天 | **排除当天/当次**（否则当天数据把自己稀释，差值被腰斩） |
| 时段评比（高峰/低谷） | 每个时段桶：**会话数 ≥ 2** 且 **桶内总学习 ≥ 20 分钟**；资格桶 < 2 个 → 不给结论 |
| 高峰/低谷落差 | `bestRate − lowRate ≥ 8` 个百分点；否则输出"各时段差别不大" |
| 趋势（近 7 天 vs 前 7 天） | 变化幅度 ≥ **10%** 才说"上升/下降"，否则"基本持平" |

## 2. 数据模型改造

### 2.1 `LearningGoal`（`models/Task.ets`）

字段不动。仅明确职责：考试类型 / 日期 / 科目 / 标语，是这四件事的唯一来源。

### 2.2 `StudyPlan` 重定义（`models/StudyPlan.ets`）

```ts
/** 长期计划的单科目标 —— 科目名必须取自 LearningGoal.subjects（唯一科目源） */
export class SubjectTarget {
  subject: string = ''
  targetMinutes: number = 0
}

export class StudyPlan {
  /** 固定单记录 id —— 保证 study_plan 表永远只有 1 行 */
  static readonly PLAN_SINGLETON_ID = 'plan:current'
  id: string = ''
  title: string = ''              // 计划名（原 longTermPlan.title）
  periodStart: number = 0
  periodEnd: number = 0           // 默认 = goal.targetDate
  subjectTargets: SubjectTarget[] = []
  /** 派生、只读 = Σ subjectTargets.targetMinutes（D3） */
  totalEstimatedMinutes: number = 0
  createdAt: number = 0
  updatedAt: number = 0
}
```

- **删除** `examType`（D1）、**删除** `tasks`（死字段）。
- `PlanTask` 若仍作 AI 输出 DTO 使用，移到 `models/PlanTaskDto.ets` 并加注释「**仅传输结构，不入库**」——现在 `PlanTask.create()` 造出来的东西从来没落过盘，留在 `StudyPlan.ets` 里会继续误导。

### 2.3 `Task` 增加归属（`models/Task.ets`）

```ts
/** 归属的长期计划 id；'' = 自由专注/未归属（不计入目标进度） */
planId: string = ''
```

- `Task.copy()` 同步该字段；`StorageService` 读写加 `plan_id` 列。

### 2.4 存储层（`services/StorageService.ets`）

- **单记录保证**：`saveStudyPlan()` 强制 `plan.id = StudyPlan.PLAN_SINGLETON_ID` 再 upsert（`ON_CONFLICT_REPLACE` 按主键，固定 id 即天然单行）。
- **`loadStudyPlan()` 必须加排序**：现在 `new RdbPredicates('study_plan')` **没有 `orderBy`**，直接取第一行 —— 而 `LongTermPlan.save()` 每次 `StudyPlan.create()` 生成**新 uuid**，表里会累积多条，**读回哪条不确定**。改为 `orderByDesc('updated_at')`，并以固定 id 优先命中。
- **幂等加列**：新增 `ensurePlanColumns()`，对 `subject_targets` / `period_start` / `period_end` / `plan_id` / `updated_at` 逐个 `ALTER TABLE ... ADD COLUMN`，包 `try/catch` 忽略"duplicate column"（`CREATE TABLE IF NOT EXISTS` 只对新装用户有效，老用户必须 ALTER）。
- 序列化：`subjectTargets` 存 JSON 字符串；`parseSubjectTargets()` 对脏数据返回 `[]`，不抛。
- **备选（更省事但不利扩展）**：因为恒为单记录，也可直接把这个对象存进 `app_kv`（项目已有 `saveKv/loadKv`），**完全免掉 schema 迁移**。代价是失去"将来支持多份计划"的空间。若本轮只求最快落地，可选它；否则走上面的表方案。

## 3. `actualDuration` 写回（新增前置步骤）

这是口径 B 的数据源，必须先做，且它本身独立、改动小。

**现状缺口**：`recordTaskTimeline()` 只在 **3 处**被调用 —— `completeCurrentTask()`（`FocusController.ets:226`）、`switchToTask()`（`:232`）、`setTaskDone()`（`:253`）；`start()` / `restore()` 里**没有初始点**，所以第一段（0 → 首次切换）无归属。

改法：

1. **补初始点**：`start()` 与 `restore()` 中在设置 `currentTaskId` 之后加一条 `taskTimeline`（`minuteOffset = 0`，`taskId = 当前任务`）。
2. **`finalize()` 里分段反算**（放在 `session.completedTaskIds` 计算之后）：
   - 把 `this.session.taskTimeline` 按 `minuteOffset` 升序排列，得到若干段 `[p_i, p_{i+1})`，段长（分钟）= 相邻差值；**末段**用 `floor(totalSec / 60)` 补齐；
   - 数组为空时退化为"整段算给第一个未完成任务"；
   - 每段把 `段长 × 60` 累加到对应 `Task.actualDuration`。
3. 口径写进字段注释：**`actualDuration` = 墙钟段长**（不细分段内休息/暂停）。
4. 落库沿用现有链路：`AppStore.endSession()` 里已经有 `for (const t of tasks) saveTask(t)`，不需要新增。
5. **顺手修掉 `models/StudyPlan.ets:7` 的不实注释** —— 它声称"实际投入由 `FocusController` 在 `finalize()` 时反算写回"，这个行为此前并不存在。改动完成后注释才成立，但措辞要改成"按 `taskTimeline` 分段反算"。

**验收**：一段 30 分钟的专注、中途切 1 次任务 → 两个任务的 `actualDuration` 之和 ≈ 1800 秒（±60 秒）。

## 4. 工作台进度聚合

### 4.1 `Metrics` 新增纯函数（必须保持"不读存储"）

`services/Metrics.ets` 顶部有明文硬规则：**全部为纯函数、不持状态、不读写存储**。所以新函数只收参数：

```ts
export interface SubjectProgressRow {
  subject: string
  targetMinutes: number
  doneEstimatedMinutes: number   // 口径 A 分子
  actualMinutes: number          // 口径 B 分子
  totalTasks: number
  doneTasks: number
  state: 'OK' | 'NO_TARGET' | 'NO_TASK' | 'OVER'
}

export interface PlanProgress {
  planTitle: string
  targetMinutes: number
  doneEstimatedMinutes: number
  actualMinutes: number
  completedPercent: number   // clamp(0,100)
  investedPercent: number    // clamp(0,100)
  overdueMinutes: number     // actual > target 时的超出量，否则 0
  unassignedMinutes: number  // 未归属/未分类任务的实际投入，只展示“+”不计百分比
  state: 'NO_PLAN' | 'NO_TARGET' | 'NO_TASK' | 'OK' | 'OVER'
  subjects: SubjectProgressRow[]
}

/** 纯计算：入参由 AppStore 组装（本期任务集 + 计划），本函数不读库 */
static planProgress(tasks: Task[], plan: StudyPlan): PlanProgress
```

- 分母 = `Σ subjectTargets.targetMinutes`。
- 任务集 = `tasks.filter(t => t.planId === plan.id)`，按 id 去重。
- **科目行来自 `plan.subjectTargets`，不由任务反推** —— 防止"没有目标的科目也画出百分比"。
- 未分类任务（`subject` 不在 targets 内）单列一行「未计入目标」：只显示实际投入与条数，**不给百分比**（对应原方案"不能伪装成百分比"）。

### 4.2 明确状态，不默认 100%

| 状态 | 触发 | UI |
|---|---|---|
| `NO_PLAN` | 没有长期计划 | 空态 + "去设置每科目标时长" |
| `NO_TARGET` | 有计划但 `subjectTargets` 为空 | 空态 + "按现有任务比例分摊"一键（D4） |
| `NO_TASK` | 有目标但本期无任务 | "还没有任务，进度 0%"，进度条空 |
| `OK` | 正常 | 主数值 = 口径 B，副信息 = 口径 A |
| `OVER` | `actualMinutes > targetMinutes` | 进度条 100% + 主数值 `实际 / 目标` + "已超出 N 分钟" + 一键上调（D6） |

### 4.3 职责边界与展示面

- **`AppStore` 统一生成**：`refreshAggregates()` 里组装入参、调 `Metrics.planProgress()`、把结果存进 `this.planProgress`，再由 `pushAggregates()` 广播（沿用 `DATA_VERSION`）。
- **页面只渲染、且走拉取式**：`Dashboard` 与 `Home` 都从 `AppStore.getInstance().getPlanProgress()` 取，**不要用 `@StorageProp` 镜像派生** —— 这正是上一轮 C3 修掉的坑（镜像 + `@Watch` 顺序不确定 → 派生值永久停旧）。
- **`Dashboard`**：`refresh()` 里删掉自己那套 `merged / allDone / allTotal` 口径（`Dashboard.ets:65-96`），改为读 `planProgress`；「总体进度」卡片标题建议改为「**目标进度**」，并加一行口径说明。
- **`Home`**：「任务完成率」是**今日计划**的口径（`dashDone/dashTotal`），与工作台的"目标进度"**不是同一个数**。两者可以并存，但**标签必须写清**（"今日任务完成率" vs "目标进度"），否则用户会当成不一致——这是上一轮 C3 那类问题的翻版。
- `Dashboard` 的「科目进度（近 30 天）」`computeSubjectProgress()`（按 `createdAt` 条数）**删除**，统一用 `planProgress.subjects`。

## 5. 单日复盘

### 5.1 新增结构指标（`Metrics`）

`Metrics.sessionStructure(s: FocusSession): SessionStructure` —— 用的就是现成的 **30 秒粒度 `timeline`**（`level 0-100` + `state`），现在这份数据只被用来画色带，一个结构量都没算：

| 指标 | 定义 | 为什么值钱 |
|---|---|---|
| `timeToFocus` | 首个 `state === FOCUSED` 的 `timeline.minute` | "进入状态要多久"，可对比可干预 |
| `longestRun` | 最长连续 `FOCUSED` 采样点数 × `TIMELINE_SAMPLE_MS/60000` 分钟 | 真正的"单段专注阈值" |
| `bouts` | `state` 由 FOCUSED → 非 FOCUSED 的次数 | 分心频率 |
| **`recoveryMedian`** | 每次分心回到 FOCUSED 的耗时中位数 | **被打断后多久能回来** —— 最可干预、最值得展示的指标，原方案完全没提 |
| `deepRatio` | `level ≥ 80` 的采样点占比 | 深度专注的成色 |
| `tailDrop` | 后 1/3 平均 `level` − 前 1/3 平均 `level` | **真实的疲劳拐点**，替代现在"取第一个 `level < 45`"的过松判定（第 1 分钟一波动就报疲劳） |

### 5.2 个人基线（`Metrics`）

`Metrics.baseline(sessions, excludeSessionId, now): Baseline`

- 窗口与门槛见 **D7**（近 7 天优先 → 扩 30 天；≥3 次会话且 ≥60 分钟总学习；**排除当天**）。
- 返回同 6 个量的中位数 + 净专注率中位数，以及 `ready: boolean` 与 `needMore: number`。

### 5.3 当天最佳时段

新增 `Metrics.bestPeriodOfDay(daySessions, dayStart)`：取当天**净专注最长且平均 `level` 最高**的一段（≥10 分钟），叠加当天真实起始时钟。

- 现在 `daySummary().bestPeriod` 复用 `Metrics.goldenWindow()`，而后者**硬过滤"最近 14 天"**（`Metrics.ets:169`）→ 看 14 天以前任意一天，`bestPeriod` 恒为空 → `dayInsight` 回退成"当天状态最好的那一段"（句子里说"那一段"却不给时间）。本项即为此修。

### 5.4 洞察与建议的生成

- `AIService.dayInsight` 签名改为接收 `structure + baseline + 差值`，**每条结论自带数字**，例如：
  - 「今天 45 分钟里进入状态用了 6 分钟，你平时是 2 分钟」
  - 「最长一段连续专注 18 分钟，比你这周的 27 分钟短了 9 分钟」
  - 「被打断 3 次，平均 4 分钟才回到专注」
- **无法比较时（`baseline.ready === false`）只报当天事实 + "还差 N 次会话"**，不做跨天结论 —— 对应原方案"单日仅在有数据时给出结论"。
- `daySuggestions` 改为**从洞察派生**，最多 3 条，优先级：
  1. `bouts` 高于基线 → 先找分心源（配合 C4 的手机使用事件）
  2. `recoveryMedian` 高于基线 → 被打断后回不来，建议缩短单段 / 加主动休息
  3. `tailDrop` 明显 → 疲劳拐点偏早，缩短单段时长
  4. `longestRun` 低于基线 → 单段太短
  5. 全部达标 → 只给 1 条保持建议
- **删除所有无条件追加的模板**（现在 `MockAIService` 里"每 45 分钟左右主动休息""练习题分两批完成"是无条件出现的）。
- 阈值不再用"≥80 / ≥60 / 其它"这种固定档。

## 6. 长期复盘

### 6.1 时段分析重写（`Metrics.habitInsights`）

这是"效果不好"的**直接原因**，四条必须一起改：

| # | 现在 | 改为 |
|---|---|---|
| 1 | **2 小时桶**，全天只 12 档 → "08:00–10:00"必然反复出现 | **1 小时桶（24 档）** |
| 2 | 高峰/低谷按**总学习时长**取（`bucketsStudy` 排序）→ "学得久"被当成"效率高"；算出的专注率只用于展示 | **专注率优先**：高峰 = 资格桶中专注率最高，低谷 = 最低；时长只做门槛 |
| 3 | 初值 `peak = low = used[0]` + 严格 `>`/`<`，多个桶相等时 **`bestWindow === lowWindow`** → 生成"你的高效时段在 08:00–10:00；08:00–10:00 偏低"的自相矛盾 | 落差门槛 `bestRate − lowRate ≥ 8` 个百分点才下结论，否则"各时段差别不大" |
| 4 | 门槛只有 `used.length === 0/1` → **2 个时段就敢下高峰+低谷结论** | 资格门槛见 **D7**（桶内 ≥2 次会话且 ≥20 分钟） |

- 窗口固定为**近 30 天**并在文案里写明 —— 现在传的是**全量 sessions、不限窗口**（`Review.ets:125`），一次成型后几乎不再变化；也与 `last30DaysSummary` 的"近 30 天"两套口径打架。

### 6.2 新增长期指标

- `Metrics.trend7v7(sessions, now)`：近 7 天 vs 前 7 天的**净专注率**与**日均净专注分钟**；变化 ≥10% 才说"上升/下降"，否则"基本持平"。
- `Metrics.streaks(sessions, now)`：连续学习天数（含今天）、最长空档天数。
- 稳定性：复用 `fiveDim` 的 σ 算法，但窗口改近 30 天（现在五维是"全历史平均"，没有任何趋势语义）。
- 科目目标完成度：直接用 §4 的 `planProgress`（依赖 C、D）。
- `Metrics.last30DaysSummary()` 保留，作为趋势图的底座。

### 6.3 建议生成

`longTermAnalysis` 改为 **1 个主要杠杆动作 + 1 个保持动作**，每条必须带数字与对比基准；样本不足时显示"还需 N 次会话 / N 天"，**不猜"正在提升"**。（现在只要 `sampleCount ≥ 3`，句式就固定为"五维最大/最小 + 最慢科目"三段，与近期数据无关。）

### 6.4 口径边界（原方案这里有个隐患）

原方案说"让 `Review`、`FocusProfile` 和 AI 文案层复用同一份指标对象"。方向对（符合"指标只在 Metrics 算"），但要注意：

- **`FocusProfile` 是持久化的**（`focus_profile` 表，且只在 `endSession` 时更新）；
- **窗口指标（近 7/30 天）是每次现算的**。

把窗口指标塞进 `FocusProfile` 会变成"落库那刻新鲜、展示时已过期"。因此定案：**窗口指标一律现算、不进 Profile；`FocusProfile` 只保留累积型字段**（`sampleCount` / 五维 / `focusThreshold` / `bestFocusTime`）。这也是避免"页面、画像、复盘各自解释数据"的正确切分。

**项目当前没有任何测试设施**：无 `entry/src/ohosTest`、无 `entry/src/test`、无 `*.test.ets`、`oh-package.json5` 里也没有 `@ohos/hypium`。在复赛周期内不建议为了这条去搭框架 → **降级为手工回归清单**：

| # | 场景 | 期望 |
|---|---|---|
| 1 | 全新用户，未设长期计划 | 工作台进度为**空态**"去设置每科目标时长"，**不显示 0% 也不显示 100%** |

| 12 | 科目名与 `LearningGoal.subjects` 不一致 | 该科目归入「未计入目标」，不给百分比（验证 D1 的单一来源规则生效） |

## 9. 实施顺序与依赖

```
A  单日复盘（结构指标 + 基线 + 建议派生 + 当天最佳时段）
   ├─ 无依赖，纯算法 + 一个页面文案，收益最快、风险最低
   └─ 可先做

B  actualDuration 写回（+ 修不实注释）
   ├─ 无依赖，改动小（start/restore 补初始点 + finalize 分段反算）
   └─ 是口径 B 的前置

C  数据模型（Task.planId / StudyPlan 重定义 / 固定单记录 / 幂等加列 / 旧数据迁移）
   └─ 无依赖，是 D 与 E 的共同前置

D  进度聚合（Metrics.planProgress + AppStore 统一生成 + Dashboard 与 Home 渲染 + 口径文案）
   └─ 依赖 B、C

E  长期复盘（1 小时桶 / 专注率优先 / 趋势 / streak / 科目目标完成度）
   └─ 依赖 C、D（"科目目标完成度"要用 D 的结果）

F  文案与说明、手工回归清单
   └─ 依赖全部
```

- **A 与 B 可并行**；原方案把 5 步并列编号，容易误以为能并行，实际上 2 依赖 1、4 依赖 1 和 2。
