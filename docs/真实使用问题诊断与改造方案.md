## Q1 · 登录太草率

### 代码事实

`services/AuthService.ets`：

| 行为 | 实现 | 问题 |
|---|---|---|
| 注册 | **没有独立注册**。首次输入任意用户名 + 任意 ≥6 位密码 → **自动建号** | 无法区分"注册"与"登录" |
| 登录 | 仅当 `storedName === name` 才校验密码 | **换个用户名就等于换账号**，旧账号仍留在本地 |
| 密码 | `djb2` 散列（`hash()`），存 KV | 注释已承认"不作为安全边界"。djb2 无盐、碰撞多，**逆推成本极低** |
| 会话 | `saveKv(LOGGED_IN,'1')` | 无 token、无过期、无并发登录控制 |
| 退出 | `saveKv(LOGGED_IN,'0')` | **用户名与密码散列仍留在本地**，且学习数据不清 |

`pages/Login.ets`：只有两个 `TextInput` + 一个按钮。**没有**：隐私政策勾选（合规硬要求）、验证码、忘记密码、第三方登录、密码可见性切换、输入长度上限、键盘类型。

### 比"草率"更严重的一条

`AppStore` 是**单例**，`sessions / tasks / profile` 只有一份。`AuthService.login()` 换用户名后：
- `AppStore.applyLoginUser()` **只改了 `nickname`**
- **`sessions / tasks / profile / goal` 完全没变**

→ 用 A 账号学了一周，退出，用 B 账号登录，**B 看到的还是 A 的学习记录、A 的画像**。这是数据隔离缺失，不是"简单"。

### 另外两个连带的初始化问题

1. `seed()` 在**首次启动时**就把 `user.nickname='刘灿'`、`goal='考研上岸' / 128 天` 写库（`AppStore.ets:106-122`）。用户在 Login 输入的名字只覆盖了 `nickname`，**goal 从来没被覆盖**。
2. `EntryAbility.onCreate` 里 `AppStore.init()` 仍是 **fire-and-forget**（未 `await`），`loadContent` 立即执行。`Mine.aboutToAppear()` 读 `getUser().aiPersonality` 时 AppStore 可能还没 init → 人格回落到默认值。

### 改造建议（两条路线，选一条）

**路线 A · 砍掉账号（推荐给竞赛 Demo）**
- 把 Login 改为「开始使用」单按钮 = 本地体验模式，无账号
- 首次进入引导两步：设昵称（必填）+ 设目标考试与日期（可跳过）
- 好处：省掉所有账号体系的坑，把工期还给专注与感知；评委也更难挑刺
- 成本：约 0.5 天

**路线 B · 补齐最小可用账号**
- 登录页拆「登录 / 注册」两态，注册需二次确认密码 + 隐私协议勾选
- 密码加盐（`salt = uuid`，存 `salt + hash`）
- 退出登录时**清空 AppStore 内存 + 停止会话**，数据按 `userId` 分表（`user` 表已有 id，给 `task/session/profile/goal` 加 `user_id` 列）
- 修正 `seed()`：**不再写死 nickname 与 goal**，让用户首次进入时自己设
- 成本：1.5–2 天

无论哪条，都要顺手修：`seed()` 不写死 goal、`EntryAbility` 改 `await init()` 后再 `loadContent`。

## Q2 · 「首页」是什么？数据来自哪里？

### 事实：登录后你看到的不是首页，是工作台

`Login.doLogin()` → `router.replaceUrl('pages/Index')`，而 `pages/Index.ets` 是：

```
Index (Tabs, 默认 tab 0)
 ├─ tab 0  工作台   ← 你看到的"首页"
 ├─ tab 1  AI 规划   (TaskPlanning)
 ├─ tab 2  复盘      (Review)
 └─ tab 3  我的      (Mine)
```

**`pages/Home.ets` 是死代码** —— 全项目 grep `pages/Home`、`from './Home'` 均为 0 命中。它才是原本设计的"首页 / 今日专注"，而且**里面那唯一的「开始专注」按钮也跟着一起废掉了**。

### 首屏每一块数据的确切来源

| 首屏区块 | 数据来源 | 真实性 |
|---|---|---|
| 「早上好，XXX」 | `AuthService` KV 里的用户名 → `applyLoginUser` → `user.nickname` → `USER_NICKNAME` | 真实 |
| 右上角头像 | `USER_AVATAR`，默认 `🧑‍🎓`，可点击换 | 真实（用户自选） |
| **考试总览「考研 / 距离考研还有 128 天」** | `AppStore.seed()` 硬编码：`title='考研上岸'`、`examType='考研'`、`targetDate = Date.now() + 128*24h` | **纯假数据，且全 App 无任何编辑入口** |
| 总体进度 `0 / 0` | `refreshAggregates()`：遍历 `tasks`，只统计 `createdAt` 是今天的 | 真实，但新用户恒为空 |
| 科目进度 | `computeSubjectProgress()`：遍历**全部历史任务**（不是今天），按 `done/total` | 口径误导（跨天累积） |
| 长期趋势柱状图 | `computeWeekTrend()`：按会话 `startTime` 分 7 天累加 `focusDuration` | 真实 |
| 近 7 天净专注时长 | `weekFocusSeconds` | 真实 |
| 净专注率 | `focusRate = todayNet / todayFocus`，其中 `todayFocus = Σ s.totalDuration` | ⚠️ **口径与复盘页不一致**（见 Q5 缺陷 7） |

### 结论

新用户首屏 = **一张假倒计时卡 + 三张空态卡**。它既没回答"今天学什么"，也没回答"现在状态如何"，更没提供"是否开始专注"——这三个才是需求文档第十节明确要求首页回答的问题。

**所以这个页面本身不是错的，错在它被当成了首屏，而真正的首页（Home）被废弃了。**

### 建议

把信息架构改回"专注优先"：

```
tab 0  专注（新首页）   ← 今日任务 + 开始专注 + 今日数据 + AI 当前建议
tab 1  AI 规划          ← 保留
tab 2  复盘              ← 保留
tab 3  工作台            ← 考试倒计时/科目进度/趋势（从首屏降级为看板）
tab 4  我的              ← 保留
```

并把 `Home.ets` 从死代码救回来作为新 tab 0（它的结构基本可用，只需按下面的 Q3 改造）。

## Q3 · 专注要突出在首页 / 可跳过规划 / AI 规划内容幼稚

### 3.1 事实：现在根本无法"直接开始专注"

全项目搜索「开始专注」，只有 3 处命中：

| 位置 | 状态 |
|---|---|
| `pages/Home.ets:269` | **死代码**（无人引用） |
| `pages/TaskPlanning.ets:597`「确认并开始专注学习」 | **唯一活着的入口** |
| `pages/Focus.ets` / `FocusBreak.ets` 的「继续专注」 | 会话中恢复用 |

而 `TaskPlanning` 是 **AI 规划 tab**。也就是说：

> **用户想专注，必须先跟 AI 聊完规划、生成任务列表、点确认，才能进入专注页。没有"跳过规划"的路径。**

这与你说的完全一致。改动很小，但它是整个产品的入口问题。

### 3.2 事实：AI 规划为什么"幼稚"

`TaskPlanning.send()` → `AIService.dialogByScene()` → `GatewayAIService.runDialog()` → `Prompts.taskDialog()`。
网关可用时走真实 `qwen-plus`；不可用时回退 `MockAIService.produceDialog()`。

**根因 1 · 提示词没有注入任何用户上下文**

`Prompts.taskDialog(personality)` 的全部输入只有 `personality` 和对话历史。**没有**：
- 用户的目标考试、学科、距考天数（`goal` 表里有，没传）
- 用户的历史画像（`FocusProfile`：黄金时段、平均专注时长、最易分心科目）
- 历史任务与完成情况（`sessions` / `tasks` 表里有，没传）
- 上次规划了什么、哪些没完成
- 用户的疑问记录（`question` 表）

→ 模型只知道"这个人在跟我要一份学习计划"，**不知道他是谁、在备考什么、卡在哪**。它只能产出通用模板。

**根因 2 · `PlanningInput` 定义了上下文字段，但页面一个字都没传**

```ts
// services/ai/PlanningService.ets
export interface PlanningInput {
  goal: string
  availableMinutes?: number      // ← 定义了
  subjects?: string[]            // ← 定义了
  preferredSubject?: string      // ← 定义了
}
```

而 `TaskPlanning.generatePlan()` 只传 `{ goal: this.composeGoal() }`（`TaskPlanning.ets:145`）。
**用户在第 2 轮说的"两个小时"被彻底丢弃**——连"可用时间"这么基础的约束都没进提示词。这就是为什么"计划"看起来和你给的信息无关。

**根因 3 · 提示词自身把任务粒度带偏**

```
【你的任务】
1. ... b. 做什么（刷题、背单词、听课、复盘、写作业…）
3. 拆成 2~5 条能立刻上手的小任务（具体到"完成 10 道级数作业题"这种粒度）
```

- 让模型"挖掘"这五项，但没说**从已有上下文里读**，于是它只能反问 + 猜。
- 示例词「背单词」「复习章节」是**通用学习动作**，对"我要学高数"这种粗目标，模型最省力的输出就是「复习定义 → 背公式 → 做例题」这类浅层任务——**正是你觉得荒堂的那种**。
- 没有任何约束说"必须基于用户的考试类型/进度/错题"。也没有给它"不知道就问，不要编"的指令。

**根因 4 · 网关不可用时会掉到占位垃圾**

```ts
// MockAIService.produceDialog(), step >= 2
return {
  reply: '好的，我帮你安排一下。',
  done: true,
  tasks: [
    PlanTask.create('优先任务块 A', '综合', 30, 0),
    PlanTask.create('巩固练习 B', '综合', 30, 1),
    PlanTask.create('整理复盘 C', '综合', 20, 2)
  ]
}
```

`producePlan()` 则是关键词硬分支（含"高数/数学/极限/导数" → 固定 4 条「复习极限章节 / 完成极限练习题 10 道 / …」）。
**只要网络抖一下、Key 过期、超时，用户就会看到「优先任务块 A」这种明显是占位符的东西** —— 演示时这是致命的。

**根因 5 · 记忆层根本没接上**

`services/ai/MemoryService.ets` + `AIService` 的 `'memory'` 场景 + `SchemaValidator.memoryValidator()` 都写好了，但**全项目零业务调用**（grep 确认：只有定义处与 Schema 校验处）。
规划链路**不读记忆**，画像更新走的是另一条路（`AIService.updateProfile` → `Metrics`）。

### 3.3 改造建议

**A. 首页加「开始专注」（0.5 天）**
- 把 `Home.ets` 恢复为 tab 0，`开始专注` 按钮放在首屏黄金位置
- 点击时分两条路：有今日计划 → 直接进 `Focus`；无计划 → 弹选择「AI 帮我规划 / 直接开始（自由专注）」
- `FocusController.start([])` 已支持空任务，`Focus.ets` 有「自由专注 / 未设定任务」分支，无需改控制器

**B. 规划页加「跳过规划」出口（0.25 天）**
- `TaskPlanning` 顶部加右上角「跳过 →」：直接用当前对话里已提到的信息走 `task_plan`，或直接 `setCurrentPlan([])` + 进 Focus
- 底部 `startBar` 在 `tasks` 为空时也显示「直接开始专注」

**C. 把上下文喂进提示词（1 天，收益最大）**

在 `TaskPlanning` 里组装上下文并传给 `PlanningInput`：

```ts
const ctx: PlanningInput = {
  goal: this.composeGoal(),
  availableMinutes: parseMinutes(this.userTexts),   // 从对话里解析"两小时"
  subjects: AppStore.getGoal().subjects,            // 真实学科
  preferredSubject: this.pendingSubject
}
```

并在 `Prompts.taskDialog()` 里插入结构化上下文段：

```
【已知的用户背景】（请基于这些信息规划，不要凭空假设）
- 备考目标：{examType}，距考试 {daysLeft} 天
- 学科：{subjects}
- 最近 14 天黄金时段：{bestWindow}
- 平均单次专注：{avgFocusMin} 分钟；建议单段不超过 {focusThreshold} 分钟
- 最近易分心科目：{hardestSubject}
- 最近 3 次未完成任务：{unfinishedTasks}
- 用户可用时间：{availableMinutes} 分钟

【硬约束】
- 任务总时长必须落在用户可用时间的 ±15% 内
- 每条任务必须点名具体内容（章节名/题型/题量/单词数），禁止"复习一下""巩固练习"这类空话
- 若背景信息不足，只追问 1 个最关键的问题，不要编造进度
```

**D. 修掉占位兜底（0.25 天）**
- `produceDialog` / `producePlan` 的兜底必须是"可信可用"的任务模板，而不是「优先任务块 A」
- 或：网关失败时**不自动出计划**，改为提示「网络不太好，我先把你说的时间记下来，你可以手动加任务」——**宁可不给，也不要给假的**

**E. 让 memory 场景真正被调用（0.5 天）**
- `AppStore.endSession()` 里把 `session` 喂给 `memory` 场景，由 `MemoryService` 决定是否更新画像
- 规划前调一次只读记忆查询，把结果塞进上面 C 的上下文

## Q4 · 没有摄像头联动、没有手表联动，专注过程太简略

这一块是**问题最集中**的地方。逐条给证据。

### 4.1 摄像头预览是静态占位

```ts
// pages/Focus.ets:161-177
if (this.perceptionMode === 'PERCEPTION_FULL') {
  Stack({ alignContent: Alignment.Center }) {
    Column() {
      Text('📷').fontSize(34)
      Text('AI 实时专注感知预览').fontSize(13)
    }
  }
  .width('100%').height(150)
  .backgroundColor(Colors.CARD)
}
```

一个 emoji + 一行文字，**没有任何真实预览**：
- 全项目 grep `XComponent` / `CameraKit` / `@ohos.multimedia.camera` → **0 命中**
- `module.json5` 的 `requestPermissions` **只有 `ohos.permission.INTERNET`** → 即使现在接入 CameraKit 也会因缺权限失败

**用户"看不到自己的状态"是真的看不到**，连"摄像头开着"这个事实都只是 UI 上的红点。

### 4.2 专注状态是固定脚本，不是感知结果

```ts
// services/FocusDetectionService.ets:105-131
const elapsed = (Date.now() - this.startTs) / 1000
const cycle = elapsed % 160
if (cycle < 45)      { FOCUSED }              // 0-45s 绿
else if (cycle < 62) { SLIGHTLY_DISTRACTED }  // 45-62s 黄
else if (cycle < 78) { FOCUSED }              // 62-78s 绿
else if (cycle < 100){ SLIGHTLY_DISTRACTED }  // 78-100s 黄
else if (cycle < 122){ DISTRACTED }           // 100-122s 红
else                 { FOCUSED }              // 122-160s 绿
```

**每 160 秒循环一次**，跟摄像头、跟用户在不在座位上完全无关。
→ 结果就是：用户去接杯水回来，状态灯可能刚好从红变绿；用户盯屏幕 2 分钟，灯自己变黄了。**演示时一眼假。**

### 4.3 干预链路是死链（这条最严重）

链路已写好一半：

```
FocusController.transitionTo()
  └─ evaluateIntervention()
       └─ InterventionEngine.evaluate()   → 产出 CompanionDecision + InterventionEvent
            └─ 落库 StorageService.saveIntervention()
            └─ if (this.onIntervention !== null) this.onIntervention(decision, event)
```

`setOnIntervention()` 已经定义（`FocusController.ets:191`），但——**全项目没有任何页面调用它**（grep 确认：只有定义处和内部触发处）。

→ **干预决策算出来了、存进库了，但永远到不了界面。** 用户在专注页看到的红框是 `focusState === 'DISTRACTED'` 的条件渲染，走的是状态机，不是干预链路。`InterventionEngine` 里的预算控制（10 min 内 2 轻 + 1 重）、人格联动、渠道选择（`watch-vibrate` / `phone-sound` / `screen-select`）**全部空转**。

同时 `InterventionEngine.recordUserFeedback()` **也没有调用方** → 你上一轮设计的"反馈回收闭环"同样没接上。

### 4.4 手表是伪造的，而且会"假装震动"

这是**诚实性**问题，跟代码注释里的承诺正好相反：

```ts
// services/SensorService.ets
private connected: boolean = true        // ← 默认已连接

isWristPresent(): boolean {
  return this.connected                   // ← 恒定返回 true
}
```

后果链条：
1. `FocusController.evaluateIntervention()` 里 `hasWatch: SensorService.getInstance().isWristPresent()` → **永远是 true**
2. `MockAIService.buildDecisionSync()`：
   ```ts
   const channel = level === 'HEAVY' && ctx.hasWatch ? 'watch-vibrate'
                 : level === 'HEAVY' ? 'phone-sound' : 'screen-select'
   ```
   → 红级干预渠道**永远选 `watch-vibrate`**
3. `pages/Focus.ets:261`：
   ```ts
   if (!SensorService.getInstance().isWristPresent()) {
     Text('（手机提醒，未连接手表，不会震动）')
   }
   ```
   → 因为恒为 true，**这句诚实提示永远不会显示**

`InterventionEngine` 的注释写着「无手表时 RED 干预 channel = phone-sound（绝不 watch-vibrate，不假装震动）」——**逻辑写对了，但输入是假的，所以承诺没有兑现。**

另外 `pages/Device.ets` 显示：

```
⌚ 华为 WATCH   已连接
   心率 71 bpm · HRV 52 ms · 动作正常
```

`SensorService.getStatusText()` 每次调用都 `Math.random()` 生成心率/HRV → **每次刷新数字都跳**。这是一个伪造的设备页。

### 4.5 专注页本身的信息密度太低

当前 Focus 页从上到下：合规栏 → 学科/任务名 → 摄像头占位 → 大计时器 → 已专注 → 呼吸灯 → 状态文字 → 任务勾选 → 红灯块（条件）→ 底部三按钮 + AI 悬浮球。

缺的是"陪伴感"的载体：
- **没有任何生理/动作信号**（心率、HRV、手腕动作都没展示，虽然 `SensorService` 有方法）
- **没有"感知到什么"的说明**（为什么现在变黄了？）
- **没有干预历史的可见性**（刚才提醒过你几次？）
- **没有当前任务的进度感**（这个任务还剩多久？）
- 呼吸灯可点（`demoCycleState`）—— 但**没有任何提示告诉用户它可以点**，演示时观众不知道

## Q5 · 复盘所有数据是怎么算出来的？

指标确实已经收敛到 `services/Metrics.ets` 这一个事实源了，这点做得好。但**有 7 处算法缺陷**，其中 2 处会让数字明显错误。

### 5.1 计时口径（`FocusController.recomputeTick`）

```ts
const dtMs = Math.min(now - this.lastTickAt, MAX_TICK_DELTA_MS)  // 5s 封顶
const dt = dtMs / 1000
this.totalSec += dt              // 墙钟：含休息 / 暂停 / 答疑
if (paused)  { this.pausedAccum += dt; return }
if (resting) { this.breakSec += dt;    return }
if (qaMode)  { this.qaSec += dt }
else if (state === FOCUSED) { this.focusSec += dt }
else { this.distractionSec += dt }
// 每累计 30s 采一个曲线点
```

### 5.2 基础口径表（`Metrics`）

| 指标 | 公式 | 代码 |
|---|---|---|
| 墙钟 | `totalDuration`（running 期间全部流逝） | `Metrics:71` |
| 总学习 | `totalDuration − breakDuration − pausedDuration` | `Metrics:86` |
| 净专注 | `focusDuration`（GREEN 累计） | `Metrics:91` |
| 分心 | `distractionDuration`（YELLOW + RED 累计） | `Metrics:96` |
| 答疑 | `qaDuration`（计入总，不计净） | `Metrics:101` |

| 黄金时段 | 近 14 天，按 2 小时分 12 桶，取总学习时长最大的桶 | `Metrics:153` |
| 专注阈值 | 各会话"最长连续 GREEN 段(分钟)"的**中位数**，取最近 3 次 | `Metrics:210` |
| 五维·效率 | `0.6 × 平均净专注率 + 0.4 × 平均完成率` | `Metrics:257` |
| 五维·专注度 | `平均净专注率` | `Metrics:258` |

### 5.3 七处算法缺陷（必须知道）

**① 最佳专注时段时长被放大 2 倍** ⭐

```ts
// Metrics.bestFocusPeriod()
if (p.level >= 70) { if (curLen === 0) curStart = p.minute; curLen++ ; ... }
...
const endClock = Metrics.clock(bestStart + bestLen)
```

`curLen` 是**采样点的个数**（每点间隔 30 秒），却被当成**分钟**加到 `bestStart` 上。
→ 连续 4 个高专注点（真实 = 2 分钟）会被显示成 4 分钟。
**修法**：`endMinute = bestStart + Math.round(bestLen * 30 / 60)`。

**② 曲线 level 是随机数**

```ts
private levelForState(s: FocusState): number {
  if (s === FOCUSED)  return 90 + Math.round(Math.random() * 8)
  if (s === SLIGHTLY_DISTRACTED) return 55 + Math.round(Math.random() * 15)
  return 25 + Math.round(Math.random() * 15)
}
```

→ **曲线形状、"最佳时段"、"疲劳点"全部建立在随机数上**。只有 `state` 序列是真的。
→ 这直接导致「最佳时段」「疲劳点」两个指标不可信，也解释了为什么曲线看起来"很漂亮但没规律"。

**修法（二选一）**：
- 快速版：level 由 state 决定固定值（绿=92、黄=62、红=30），曲线变阶梯，但**诚实**
- 真实版：用感知置信度 / 分心时长占比算一个连续分数

**③ 学习习惯洞察的「低谷时段」和「建议」是硬编码**

```ts
// Metrics.habitInsights()
return {
  bestWindow: ..., bestRate: ...,
  lowWindow: '晚间 21 点后',        // ← 写死
  lowNote: '容易分心',              // ← 写死
  advice: '难题优先安排上午攻克，晚间以复习和轻量整理为主。'  // ← 写死
}
```

而且 `bestRate` 的口径也错了：它累加的是**全部会话**的净专注率平均，不是 `bestWindow` 这个时段内的净专注率。

**修法**：低谷时段 = 12 个桶里总学习时长最少且 < 均值的桶；`bestRate` 只统计落进 `bestWindow` 的会话；建议由低谷/高峰对比生成。

**④ 两套"最易分心科目"口径并存，且都没用对**

| 实现 | 口径 | 返回 |
|---|---|---|
| `Metrics.easyDistractionTask()` | 分心率最高的会话 | `session.title`（不是学科） |
| `Review.hardestSubject()` | **完成率最低**的学科 | `"XX类任务"` |

两者都不等于"最易分心科目"。UI 用的是后者（`Review.ets:120`、`Review.ets` 的 AI 建议），语义是"进度最慢"。

**⑤ 专注阈值的折算不可靠**

```ts
runs.push(best * 0.5)  // 采样粒度约 30s → 折算分钟
```

但 `sampleTimeline()` 有两个触发点：每累计 30 秒**一次**，以及**每次状态切换**时也调一次。→ 采样间隔不均匀，`× 0.5` 的折算只在纯连续段成立。

**⑥ 稳定性会直接归零**

`σ > 0.3 → stability = 0`。一个专注率在 60%~95% 之间波动的用户，画像里"稳定性"直接是 0，看起来像"完全不稳定"。建议改为连续映射（如 `σ > 0.35 → 触底但不为 0`）。

**⑦ 净专注率有两套分母**

| 位置 | 分母 | 结果 |
|---|---|---|
| `AppStore.refreshAggregates()` → 首屏/工作台 | `Σ totalDuration`（**含休息和暂停**） | 偏低 |
| `Metrics.netFocusRate()` → 复盘页 | `Σ (total − break − pause)` | 偏高 |

→ **同一个用户同一天，首屏净专注率和复盘页净专注率对不上。** 评委一对账就会发现。

**修法**：`refreshAggregates()` 改为调用 `Metrics.netFocusRate()` 汇总，不要自己算。

### 5.4 还缺的复盘能力

- **任务级归因没有真正输出**：`FocusSession.taskTimeline` 已经在记录（`completeCurrentTask` / `switchToTask` 都会 `recordTaskTimeline()`），`StorageService.saveTaskTimeline()` 也落库了，但**没有任何页面/服务读它**。所以"这个任务在第 N 分钟开始分心"这类洞察目前生不出来。
- **干预记录没展示**：`session.interventions` 有数据，复盘页没有对应区块。
- **`FocusProfile.weeklyTrend` / `monthlyTrend` 是死字段**：`FocusProfile` 里定义了，`StorageService` 读写它们，但**没有任何代码写入**（画像更新走 `updateProfile`，只写五维 + sampleCount）。

## Q6 · 三个入口有什么区别？为什么冗杂？

### 6.1 全部规划 / AI 入口清单

| # | 入口 | 位置 | 目标页 | 实际做什么 | 状态 |
|---|---|---|---|---|---|
| 1 | **AI 规划** | Index tab 1 | `TaskPlanning` | 对话式生成今日任务 → **唯一能开始专注的入口** | 活的 |
| 2 | **和考伴聊聊** | 我的 → 菜单 | `AICompanion` | 自由聊天 → `AIService.chat()` → `MockAIService.knowledgeAnswer()` | 活的，但语义错 |
| 3 | **规划提升方案** | 复盘 tab 底部按钮 | `pushUrl pages/TaskPlanning` | **又开一个 TaskPlanning 实例** | 活的，重复 |
| 4 | ~~AI 智能规划~~ | `Home.ets` | `pushUrl TaskPlanning` | — | **死代码** |
| 5 | 查看详细报告 | 复盘 tab | `pushUrl pages/StudyReport` | 读 `AppStore.currentReport` | ⚠️ **坏链** |

### 6.2 具体问题

**问题 1 · 「和考伴聊聊」回答的是知识点，不是规划**

`AIService.chat()` → `MockAIService.chat()` → `knowledgeAnswer(q)`。这个函数是**关键词题解**：

```ts
if (q.includes('洛必达')) return '洛必达法则适用于 0/0 或 ∞/∞ 型未定式…'
if (q.includes('导数') || q.includes('链式')) return '链式法则是复合函数求导的核心…'
...
return '这个问题我记下了。按我目前的模拟知识库，先给你一个方向：把它拆成「定义 → 适用条件 → 典型例题」三步逐步击破。回到专注后，我会把它写进本次复盘。'
```

而 `AICompanion` 的**第一个快捷提问就是「帮我规划今天的学习」**。
用户点它 → 命中兜底 → 得到「把它拆成定义→适用条件→典型例题三步」这句和规划毫无关系的话，**而且结尾还写着"回到专注后"**——用户根本没在专注。

同理「为什么我最近总是容易分心？」→ 命中 `'分心'` 分支 → 返回通用的"把任务切成更小的块"，**完全不看这个用户的真实数据**（虽然有 `sessions` 可以算）。

**问题 2 · 「规划提升方案」开第二个实例**

`TaskPlanning` 同时是：
- `@Entry` 页面（`main_pages.json` 里注册）
- `Index` 的 TabContent 子组件

`Review` 用 `router.pushUrl('pages/TaskPlanning')` → 创建**第二个独立实例**。
两个实例的 `messages` / `tasks` / `turns` / `history` 是**各自独立的 @State**，互不同步。用户在复盘页规划完回到 tab 1，会发现 tab 1 还是旧的对话。

**问题 3 · 「查看详细报告」是坏链**

```ts
// pages/StudyReport.ets:27-33
const report = AppStore.getInstance().getCurrentReport()
const session = AppStore.getInstance().getCurrentSession()
if (report === null || session === null) {
  this.hasData = false   // → 显示"还没有可展示的复盘"
  return
}
```

`currentReport` / `currentSession` **只在 `endSession()` 里被赋值，是内存态**。
→ 只要用户不是"刚从专注页结束"，从复盘页点「查看详细报告」**必然看到空页**。
而 `StorageService.loadReport(sessionId)` 已经写好了，只是没人调用。

**问题 4 · 三个入口都没有明确边界**

用户看到的是三句几乎同义的话：
- 「AI 规划 —— 按目标智能分析，合理安排今天的时间」
- 「和考伴聊聊 —— 长期陪伴 · 智能答疑」
- 「规划提升方案」

他不知道哪个该在什么时候用。

### 6.3 改造建议

**A. 明确职责边界（1 句话原则）**

| 入口 | 职责 | 不该做的事 |
|---|---|---|
| **专注（新首页）** | 开始专注、看今日任务与数据 | 不做长对话 |
| **AI 规划** | 只做「产出今日任务清单」 | 不做知识答疑 |
| **答疑** | 只做「回答问题」（从专注页进入，带会话上下文） | 不做规划 |
| **复盘** | 只做「看结果、给建议」 | 不直接跳到规划，改为"基于本次复盘生成下一次计划"（带数据进规划） |
| **我的 → 和考伴聊聊** | 只做「情绪陪伴 + 状态解释」 | 不做知识题解 |

**B. 合并重复入口的具体做法**

1. **「规划提升方案」改为带上下文跳转**：不要只 `pushUrl`，而是把一个"复盘上下文"参数传过去，让它变成「基于本次复盘调整计划」，并在 `TaskPlanning.aboutToAppear` 里读取。同时把 `TaskPlanning` **从 TabContent 里摘出来**，只作为独立页（tab 1 改为一个轻量的"今日计划"摘要页，点进去才进完整规划聊天）。
2. **「查看详细报告」改为按 sessionId 从库读**：把 `Review` 的会话列表项传 `sessionId`，`StudyReport` 用 `StorageService.loadReport(id)` 兜底。
3. **「和考伴聊聊」的 `chat()` 分流**：先判断意图——
   - 命中"规划/安排/计划" → **跳转 `TaskPlanning`**（而不是返回文本）
   - 命中"分心/状态/效率" → 走一条**读真实数据**的分析路径（`Metrics.last30DaysSummary` + `habitInsights`）
   - 否则才走 `knowledgeAnswer`
   并在 UI 上把三个能力做成**显式按钮**，而不是让用户猜。

**C. 删掉死代码**
`pages/Home.ets` 要么复活为 tab 0（推荐），要么删除。**不要让它躺着**——它里面那句注释「首页唯一的对话式规划总入口」已经在误导后来人。

## Q7 · 专注中问 AI 跳到了「规划今日学习」

### 我查到的事实

我把全项目所有 `pushUrl` / `replaceUrl` 过了一遍，结论是：

| 从 | 到 | 位置 |
|---|---|---|
| 工作台 | `Focus`（replaceUrl） | `Dashboard.ets:56` |
| 规划页 | `Focus`（replaceUrl） | `TaskPlanning.ets:259` |
| **专注页 → AI 按钮** | **`AIChat`（pushUrl）** | **`Focus.ets:103`** |
| 专注页 | `FocusBreak`（pushUrl） | `Focus.ets:94` |
| 专注页 | `StudyReport`（replaceUrl） | `Focus.ets:118` |
| 答疑页 | `router.back()` | `AIChat.ets:33,86` |
| 休息页 | `StudyReport` | `FocusBreak.ets:50` |
| **复盘页底部「规划提升方案」** | **`TaskPlanning`（pushUrl）** | **`Review.ets:1009`** |
| 复盘页「查看详细报告」 | `StudyReport`（pushUrl） | `Review.ets:945` |
| 我的 → 和考伴聊聊 | `AICompanion`（pushUrl） | `Mine.ets:181` |

**代码里不存在「专注页 → 规划页」的直接路径。** 专注页的 AI 按钮指向的是 `pages/AIChat`。

### 所以有两种可能，需要你确认是哪一种

**可能 A · 两个页面长得太像，被当成了同一个页（我认为概率更高）**

| | 规划页 `TaskPlanning` | 答疑页 `AIChat` |
|---|---|---|
| 顶部标题 | 「AI 任务规划」+「AI 助手在线」 | 「正在答疑」+ 答疑计时 |
| 气泡 | 💡 图标 + 米色气泡 | 💡 图标 + 卡片色气泡 |
| 输入框 | `说说你今天想学什么…` | `输入你的问题…` |
| 底部按钮 | `确认并开始专注学习` | `返回专注` |

**两页的视觉语言几乎完全相同**（同一个 💡、同款气泡圆角、同款胶囊输入框 + 发送按钮）。在专注中点 AI 之后再看到这样一屏，确实很像"又回到规划页了"。

而且更关键：**答疑页完全不体现"我在你的专注会话里"** —— 没有当前任务、没有剩余时间、没有"答疑结束后回到专注"的明确链路（只有一个底部按钮）。

**可能 B · 真的发生了页面替换**

如果确实是"页面变成了 AI 任务规划"，那只可能是导航栈被**混用 `replaceUrl` 与 `router.back()`** 打乱了：

- 进 `Focus` 的两个入口都用 **`replaceUrl`**（`Dashboard:56`、`TaskPlanning:259`）→ 会把 `Index`（含 Tab 状态）整个换掉
- 出 `Focus` 时 `onBackPress()` 又用 `replaceUrl('pages/Index')`（`Focus.ets:48`）
- `StudyReport.finish()` / `AIChat.back()` 用 **`router.back()`**

当栈里只剩一项时，`router.back()` 的行为是"退出应用"或"无操作"，而不是回到某个中间页。不同 DevEco/API 版本表现不一致。**这是导航架构层面的隐患，不管 Q7 是不是它引起的，都值得修。**

### 无论哪种可能，都建议这样做

1. **统一导航模型**（0.5 天）
   不要混用 `replaceUrl` / `back()`。建议：
   - `Index`（Tabs）是唯一根页，**永不 replace**
   - 所有二级页面（Focus / FocusBreak / AIChat / StudyReport / TaskPlanning-独立态）统一 `pushUrl`
   - 返回统一 `router.back()`
   - 或者升级到 HarmonyOS 推荐的 **`Navigation` + `NavPathStack`**，Tab 与详情页的关系会清晰很多（顺带为 C3 一多适配铺路）

2. **给聊天页加场景标识**（0.25 天，收益很高）
   - 答疑页顶部固定一条：「正在答疑 · 本次专注 42:36 · 结束后自动回到专注」，并把当前任务名带上
   - 答疑页背景色/主色与规划页做区分（例如答疑用蓝、规划用绿——你已经在用 `Colors.CHAT_ACTION` 绿色了，答疑可以换一个）
   - 答疑页底部按钮改为 `← 回到专注（继续计时）`，明确是"回去"而不是"进入"

3. **答疑页不需要显示规划相关内容**
   现在答疑页的结构完全可以化简：只有消息列表 + 输入框 + 返回按钮，**去掉任何"任务/计划"字样**。

## ⚠️ 一个必须先处理的安全问题

`services/ai/BridgeConfig.ets:26-27` 把**真实大模型 API Key 硬编码在客户端源码里**：

```
static AI_API_KEY: string = 'sk-ws-H.PDYRMEE...'
```

而且 `BridgeConfig.useGateway = true`（默认启用）。
- 这个文件在 git 里（`git log` 显示已提交过的版本），**Key 已经进入仓库历史**，即使现在删掉也仍然可从历史恢复
- 客户端持有长期 Key = 任何人反编译 APK/HAP 即可盗用你的额度
- 与你自己在文件注释里写的「硬规则 §10：API Key 只放后端，客户端代码不得出现」直接冲突

**建议动作（今天做）**：
1. 到阿里云控制台**吊销这把 Key**，重新生成一把
2. 新 Key 只放在本地不纳入 git 的文件（如 `BridgeConfig.local.ets`，加入 `.gitignore`），或直接搭一个最小 BFF 转发
3. 提交前用 `git filter-repo` / BFG 清历史（或直接接受"这把 Key 已泄露"的事实，但至少别让新的进仓库）
4. 竞赛提交的源码包里**不要包含真实 Key**——评委拿到源码就等于拿到 Key
