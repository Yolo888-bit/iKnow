## 2. P0 · 会当场翻车 / 会被判定造假 / 会造成实际损失

### P0-1 ⚠️ 用户「同意授权」的那一刻，文案与实现完全相反

这是本轮最严重的一条。**用户在被告知"不上传"的同时授权了上传。**

**用户看到的（三处，全是正面承诺）：**

| 位置 | 原文 |
|---|---|
| `pages/Home.ets:95` | 授权弹窗：「开启后，我会用前置摄像头在本地感知你的专注状态，**画面不出端、不上传、不保存**。」 |
| `pages/Focus.ets:327` | 实时预览正下方：「前置预览 · 本机渲染，**不上传、不保存** · 检测到 N 个摄像头」 |
| `pages/Login.ets:111` | 首屏：「不需要注册账号，**数据只存在本机**」 |

**实际发生的：**

```ts
// services/ai/GatewayAIService.ets:428-438
type: 'image_url',
image_url: { url: `data:image/jpeg;base64,${GatewayAIService.toBase64(f)}` }
// → POST 到 BridgeConfig.ets:24
//   https://ws-2f33030lijt758d4.cn-beijing.maas.aliyuncs.com/compatible-mode/v1

// services/ObservationQueue.ets:154-162
const dir = `${StorageService.getInstance().filesDir()}/obs/${sessionId}`
fileIo.writeSync(file.fd, frames[i])   // 帧同时落盘
```

**唯一说对的地方**是 `pages/Privacy.ets:70`：「片段会上传到云端做「在做什么」识别，并保存在本机供你复盘」——
也就是说**同一个 App 里，授权前的文案在否认，隐私页在承认。**

**为什么这条比"功能没做完"严重得多：**
- 竞赛评审如果追问数据流向，这不是"未完成"，是"误导用户"；
- 它出现在用户**做出同意决定**的那一屏，性质最恶劣；
- 而你们第六轮的架构（手表粗筛 → 抓拍 → 云端 → 规则）本身是**合理的、可辩护的**——完全没必要用一句假话去掩护它。

**修法（半天，纯文案 + 一处逻辑）：**
1. `Home.ets:95` → 「开启后，我会在感知信号触发时抓拍 2~3 秒的短片段，**上传到云端识别你在做什么**，并保存在本机供你复盘。你也可以选择仅计时模式。」
2. `Focus.ets:327` → 「抓拍片段会上传云端识别 · 可随时在隐私页清除」
3. `Login.ets:111` → 「不需要注册账号，学习记录存在本机」（删掉绝对化的"只"）
4. **或者**反过来：如果决定不上传，就把 `GatewayRecognizer` 的接入关掉，只保留本机渲染。
   → **现在的状态（代码上传 + 文案否认）是唯一一种不能留的状态。** 二选一，见 §5 待确认第 1 条。

### P1-2 摄像头权限没开时，**整条感知链是断的**

```ts
// services/FocusController.ets:269-273
if (PermissionService.getInstance().snapshot().camera) {      // ← 权限门在这里
  FocusDetectionService.getInstance().start((r) => { this.onDetection(r) })
}
// services/FocusDetectionService.ets:49-52
start(cb): void {
  this.callback = cb
  if (!PermissionService.getInstance().snapshot().camera) { return }   // ← 又一道门
}
// :152-165 submit() 的扩散前提：
if (this.callback !== null) { ... }     // callback 为 null → 只改内存、不通知任何人
```

**连锁后果**：默认状态下用户不点首页的「开启感知」→ `start()` 从不被调用 → `callback` 恒为 `null` →
`WatchEventEngine` → `onWatchEvent` → `svc.submit()` 这条链**每一环都算完了，最后一环没人接**。

而同时 **`Focus.ets:551` 的信号控制台照常显示**（`simOn()` 默认 `true`，见 P1-13），用户点「紧张92」「一键模拟分心」——
**HR 数字在变，但状态灯永远不亮、永远不来干预。** 用户/评委的结论只会有一个：这套感知是假的。

**修法（几行）：** 把"感知结论的订阅"与"是否开摄像头"解耦——`start()` 无条件注册 `callback`，权限只决定"要不要开摄像头 / 走不走视觉识别"。

### P1-3 上一段会话的分心状态会「穿越」到下一段

```ts
// FocusDetectionService.ets
private lastState: FocusState = FocusState.FOCUSED   // :18  会话间不重置
stop(preserveOverride = false) { ... this.manualOverride = null }   // :81-90  只清 override
start(cb) { this.callback = cb; ... this.callback(this.current()) } // :49/65 立刻回放一次
private current() { r.state = this.lastState; ... }                 // :142  取的是上一段的结论
resetOverride() { this.manualOverride = null; ... }                 // :93-96  唯一想用来清理的方法，零调用
```

**用户会遇到**：上一段专注以"看手机"（红）结束 → 下一次开始专注，约 6 秒后**无端变红并弹出干预卡**。
`FocusController.resetCounters()`（`FocusController.ets:342-363`）清了 `lastDetail`/`lastConfidence`，但清不到 `FocusDetectionService` 内部的 `lastState`。

**修法（3 行）：** `start()` 里复位 `lastState = FOCUSED; lastDetail = ''; lastConfidence = 0`。

### P1-4 「结束」按钮可能**永久失效**

```ts
// pages/Focus.ets:271-284
private async endFlow(showReport: boolean): Promise<void> {
  if (this.ending) { return }
  this.ending = true
  await AppStore.getInstance().endSession()    // ← 无 try/catch
  this.ending = false                          // ← 抛错就永远不会执行到
```

`AppStore.endSession()` 内部串了 **6 个 await 存储写入 + `ReportService.buildReport`**，任何一步 reject 都会抛出。
`pages/FocusBreak.ets:43-51` 是同样的写法。

**用户会遇到**：点「结束 / 生成复盘」后卡在原地，之后所有结束类按钮**静默失效**（`if (this.ending) return`），
没有任何提示，只能杀进程。杀进程后由于快照还在，甚至可能被判定为"崩溃未恢复"。

**修法：** `try { ... } catch { toast('保存失败，请重试') } finally { this.ending = false }`。

|---|---|---|

| `FocusDetectionService.start` | ✅ | ✅ |

### P1-6 息屏 / 后台的时长被 **5 秒封顶**

```ts
// services/FocusController.ets:372
const dtMs = Math.min(now - this.lastTickAt, FocusTuning.MAX_TICK_DELTA_MS)   // 5000
```

注释说明是为了"防差值爆炸"，逻辑上没错，**但代价正好砸在本产品的核心场景上**：
有手表 + 摄像头这条产品线的**全部前提**就是"学生的手不在手机上"。

**用户会遇到**：把手机扣在桌上、或锁屏学习 30 分钟 → 回来「本次已进行」只涨了 **5 秒**。
→ 时长严重偏小 → `focusRate` 失真 → 复盘数据不可信 → 用户不再相信任何数字。

**修法：** 用「段（segment）」模型记录 `{state, startTs}`，状态切换时以 `Date.now() - startTs` 结算——即你们
第三轮文档 A2 已经写好的方案，**至今未落地**。如果时间紧，最小改动是把上限从 5s 提到 60s（仍不完美，但不再荒谬）。

## A1 · 「一键模拟分心」延迟过高

### 根因（实测 5~15 秒，最坏 60 秒）

原实现是"改输入信号 → 等真算法自己反应过来"，链路上有 4 段等待叠加：

| 段 | 等待 | 出处 |
|---|---|---|
| ① 基线尚未建成则完全不判定 | 4 个合格窗口；时基 ×30 下约 **8 秒** | `FocusTuning.BASELINE_MIN_WINDOWS = 4` |
| ② 判定只在窗口关闭时发生 | 一个虚拟 60s 窗口（×30）≈ **2 秒** | `HRV_WINDOW_MS = 60_000` |
| ③ 触发节流 | 最小间隔 **60 秒** / 同因冷却 **3 分钟** | `MIN_TRIGGER_GAP_MS` / `TRIGGER_COOLDOWN_MS` |
| ④ 状态机去抖 | 红/黄需持续 **5 秒** | `DWELL_RED_TO_YELLOW_MS` |

而且"看手机"这一档**在信号上根本撞不到触发条件**：
`PHONE` 阶段的加速度方差约 3.1e-4，落在 `MOTION_STILL_VAR`(2e-4) 与 `MOTION_HIGH_VAR`(2e-3) 之间，
既不"大幅移动"也不"久坐不动"；`AROUSAL_SHIFT` 又要求 RMSSD 相对**个人基线**下降 35%
且心率上升 8 bpm —— 基线刚建成时不可能满足。**所以这条按钮在信噪层永远出不了结论。**

### 方案：把"模拟"分成两层，各自诚实

| 层 | 做什么 | 走哪条链路 | 延迟 |
|---|---|---|---|
| **① 状态注入** | 选 7 种云端可识别状态，直接注入一条"云端识别结果" | 规则组合 → 干预预算 → 状态机 → UI（**全是真实链路**） | 立即 |
| **② 信号注入** | 改心率 / HRV / 血氧 / 动作，切换合成信号阶段 | 真实 SQI 门禁 → 基线 → 触发判定 → 节流 | 约 1.2 秒 |

落地：

```ts
// services/FocusController.ets —— 状态注入
simulateObservation(activity: string, confidence: number = FocusTuning.SIM_INJECT_CONFIDENCE): boolean
// services/FocusController.ets —— 信号注入（切换阶段后强制结算一次）
simulateWatchPhase(activity: string): boolean
// services/WatchEventEngine.ets（新增）
evaluateNow(): void            // 不等 60s 窗口到期，立刻用已累积样本结算
clearTriggerThrottle(): void   // 只清"最小间隔/同因冷却"，保留单会话配额
```

要点：
- 状态注入路径上，`onObservation` 会把这次结论标记为"人工确认"（`manualInject`），
  跳过去抖与升级冷却，用完即清 —— **只影响这一次**；
- 信号注入路径上，`settleWindow(nowMs, forced)` 只放宽**结算时机**（不因样本少而丢弃、
  必要时用当前窗口先把基线建起来），**阈值语义一处未改**；
- 界面上如实写明："状态注入立刻生效；信号注入的结论依赖信号强度，不保证每次都有结论"。

估时：0.5 天（已落地）

## A2 · 退出专注后「今日数据」未刷新

### 根因（两处，都会让"统计同步"被跳过）

**(1) `endSession()` 没有兜底，一次落库异常就整段跳过**

```ts

await this.refreshAggregates()      // ← 上面任何一步抛错，这一行永远不执行
```
`refreshAggregates()` 是**唯一**把 `TODAY_FOCUS_SEC / TODAY_DONE_TASKS / DATA_VERSION`
写进 AppStorage 的地方 —— 它被跳过，首页/工作台就停在旧值。
同理 `Focus.endFlow()` 里 `this.ending = false` 也在 `await` 之后，异常时"结束"按钮会永久失效。

**(2) 退出入口有 4 个，没有任何统一出口**

`Focus.endFlow` / `FocusBreak.endFlow` / `Index.endFocusFromRoot` / `TaskPlanning:339`
各自调 `endSession()`，任何一个写法不同步，用户看到的就是"退出了但今日数据没变"。
另外 `currentPlan`（今日任务的完成状态）在会话结束后**没有重读**，
所以专注中勾选完成的任务不会反映到首页/工作台的今日任务上。

**(3) 顺带：首页勾选任务不重绘**

```ts
// pages/Home.ets:318（改前）—— 与第五轮修过的 Review 同源问题
this.plan = AppStore.getInstance().getCurrentPlan()   // 同一引用 → @State 不重绘
```

### 方案

```ts
// store/AppStore.ets（新增）—— 会话结束后的统一同步
async syncAfterSession(): Promise<void> {
  // 重读会话 / 任务 / 今日计划 → 重算聚合 → 广播响应式刷新（DATA_VERSION++）
}
```
- `endSession()` 的落库段改为 `try/catch`，`finally` 里必调 `syncAfterSession()`；
  没有进行中的会话时也同步一次（避免"以为结束过了"）；
- 画像更新移到 `syncAfterSession()` **之后**（它依赖最新会话列表）；
- 4 个退出入口全部 `try/catch/finally`：异常也同步统计、`ending` 一定复位；
- `Index` 切 Tab 到「专注」(0) /「工作台」(3) 时补一次 `refreshAggregates()`
  —— 这两个页是 Tabs 常驻子页，退出专注不会重走 `aboutToAppear`；
- `Home` 勾选任务改 `.slice()` 并同步刷新派生值。

估时：0.5 天（已落地）

## A5 · 模拟工作台状态与云端可识别状态的对齐

### 核对结果：**不一致**，需对齐并扩充

| 来源 | 取值 |
|---|---|
| 云端模型实际可识别（`Prompts.activity()`，权威） | 做题 / 看书 / 看手机 / 趴桌 / 离开 / **多人** / **无法判断**（7 个） |
| 工作台原来的阶段按钮 | 静坐(PREPARE) / 学习(STUDY) / 看手机(PHONE) / 休息(REST) / 离开(ABSENT)（5 个） |
| 模拟识别器的映射 | PREPARE→看书 / STUDY→做题 / PHONE→看手机 / REST→趴桌 / ABSENT→离开 |

不一致点：
1. 缺 **多人**、**无法判断** 两个取值 —— 云端能给出来，工作台却选不了；
2. 命名不统一（"学习" vs "做题"、"休息" vs "趴桌"、"静坐" vs "看书"），
   用户在工作台选的和复盘时间线里看到的对不上。

### 方案：建立单一映射源 `SimActivity`

```ts
// services/WatchSignalSimulator.ets（新增并导出）
export class SimActivity {
  static readonly ALL: string[] = ['做题', '看书', '看手机', '趴桌', '离开', '多人', '无法判断']
  static readonly DISTRACTING: string[] = ['看手机', '离开']   // 触发干预
  static readonly LIGHT_ONLY: string[] = ['趴桌']              // 轻提示
  static readonly LEARNING: string[] = ['做题', '看书']         // 回到专注
  static phaseOf(activity: string): string      // 状态 → 合成信号阶段
  static activityOf(phase: string): string      // 阶段 → 云端状态
  static effectOf(activity: string): string     // 该状态在当前规则下会产生什么结论
}
```

- 工作台的 7 个选项直接来自 `SimActivity.ALL`（**与云端取值逐字一致**）；
- `SimulatedRecognizer` 与 `WatchSignalSimulator` 的映射改为共用这一份，不再各写各的；
- 每个状态在界面上直接标出结论，避免"点了没反应"的误解：

| 状态 | 界面提示 |
|---|---|
| 看手机 / 离开 | 判定分心 → 触发干预 |
| 趴桌 | 判定轻度分心 → 轻提示 |
| 做题 / 看书 | 确认学习中 → 回到专注 |
| 多人 / 无法判断 | **不产生结论（宁可不提示，也不猜）** |

**关于"手表只识别 3 种动作"的问题**：真实手表的输入侧确实只有 3 类触发
（`MOTION_HIGH` / `STILL_LONG` / `AROUSAL_SHIFT`），这是**信号侧**；
而工作台要模拟的是**云端识别侧**的取值，两者不是一回事。因此按"能识别更多则同步扩充"处理，
对齐到完整的 7 种。（安全真机若接入标准 HRS，也仍走同一条 `WatchEventEngine`，无需改动。）

估时：0.5 天（已落地）

## A6 · 学习习惯洞察的数据来源与生成逻辑

**属实性核实：✅ 属实。** 算法（`services/Metrics.ets:444-501`）确实是真实计算、
无硬编码，但 `pages/Review.ets` 只渲染结果，**没有任何一句说明数据从哪来、怎么算出来的**，
用户无法判断这是"规则结论"还是"AI 猜的"。

处理：在「复盘 → 学习习惯洞察」区块标题下如实写明口径：

> 数据来源：取每一次已完成专注的**开始时间**，按每 2 小时归入一个时段（全天 12 个时段）；
> 时段专注率 = 该时段的净专注时长 ÷ 该时段总学习时长（总学习 = 墙钟 − 休息 − 暂停）。
> 生成逻辑：高峰 = 总学习时长最多的时段，低谷 = 总学习时长最少的时段；
> 若低谷的专注率比高峰低 10 个百分点以上，记为「容易分心」，否则记为「投入偏少」。
> 建议由这两者的对比自动生成，没有写死的文案；只统计到一个时段时会如实说明，不做外推。

估时：0.2 天（已落地）

## B1 · 结束专注后首页「今日数据」仍不更新 → 定案

### 结论

**不是上一轮修的那条链没修好，而是第 5 个出口从来没被覆盖。**

上一轮修的是「正常结束」这条链，它**现在是通的**（逐项核实过，不是猜测）：
- 4 个结束入口（`Focus.ets` / `FocusBreak.ets` / `Index.ets` / `TaskPlanning.ets`）都 `await endSession()`；
- `endSession()` 的落库段有 try/catch，异常也必走 `syncAfterSession()`；
- `pushAggregates()` **先写** `TODAY_*`，**最后**才写 `DATA_VERSION` → `Home.ets` 的 `@Watch` 触发时其它值已是新的，无竞态；
- 口径一致：`Metrics.wallClock() = s.totalDuration`，`Home` 显示的 `liveFocusSec()` 用的是同一个 key。

### 断点：崩溃/被杀后「恢复上一次会话 → 结束」

```ts
// services/FocusController.ets —— restore()（节选）
this.session = new FocusSession()
this.session.id = snap.sessionId
this.session.status = SessionStatus.RUNNING
this.session.perceptionMode = snap.perceptionMode
// ← 没有 this.session.startTime
```
```ts
// models/SessionSnapshot.ets 的全部字段
sessionId / ts / totalSec / focusSec / distractionSec / qaSec / breakSec /
currentTaskId / state / perceptionMode
// ← 没有 startTime
```
`finalize()` 也没有兜底。于是这条路径落库时 `start_time = 0`。

而"今天"的判定是：
```ts
// store/AppStore.ets:402
if (TimeUtils.isSameDay(s.startTime, now)) { todayFocus += Metrics.wallClock(s) }
// utils/TimeUtils.ets: isSameDay 用 new Date(a) 取年月日
```
`new Date(0)` = **1970-01-01** → 恒 `false` → **这次会话永远不计入今日**。

### 影响面（比"首页"大得多，这是要修正遗留 #2 的地方）

凡是按日期聚合的地方都会漏掉这条记录，而且**不报错、完全静默**：
| 位置 | 后果 |
|---|---|
| 首页 / 工作台「今日数据」 | 今日时长、净专注率不动（用户本次报的现象） |
| 工作台「长期趋势」柱状图 | 那一天的柱子为 0 |
| 复盘「近 30 天学习表现」 | 该会话不参与趋势与三日汇总 |
| 复盘「学习习惯洞察」 | 时段归属落空（`Math.floor(hours*60/120)` 落在 0 点桶或越界被跳过） |
| 复盘「按天复盘」 | 选那一天看不到这次会话 |

### 为什么开发期特别容易踩

每次重新安装/杀进程都会留下 `ACTIVE_SESSION_ID` + 快照（30 分钟内有效）→ 下次启动弹恢复弹窗 →
**只要不点「放弃」，就走进这条路径**。开发期几乎每次测试都会命中。

### 修法（建议两条都做，互为保险）

1. **堵源头**：`SessionSnapshot` 增 `startTime` 字段，`writeSnapshot()` 写入，`restore()` 恢复；
2. **兜底**：`finalize()` 里 `if (session.startTime <= 0) session.startTime = Math.max(0, session.endTime - session.totalDuration * 1000)`
   —— 即遗留 #2 里提到的"按现在 − 已计时长反推"，这条可以先做，1 行。

**验收**：杀进程 → 重启 → 恢复弹窗点「结束本次」→ 首页今日时长与"正常结束"路径一致；工作台当天柱子非 0。

```ts
只说到"复习高数级数"这种程度是不够的，**不能就此出计划**。你必须逐项问清下面这些，
```

## B3 · 长期复盘「练习内容总结」横向溢出

### 结论：属实。宽度预算从 360vp 一路缩到 124vp，而标签的自然宽约 200vp

```ts
// pages/Review.ets:1017-1112（区块 1048-1112）
Text(`累计完成 ${this.summary.completedTasks} 个任务`)   // :1084  无 layoutWeight / maxLines / constraintSize
Text(`净专注率 ${this.summary.focusRate}%`)              // :1093  同上
```
| 环节 | 宽度 |
|---|---|
| 屏宽 | 360 |
| 页 `padding(20)` | −40 → 320 |
| 该行两个 `layoutWeight(1)` + `space: 16` | 每卡 152 |
| 卡内 `padding(14)` | 内容 **124** |
| 两个标签自然宽（fontSize 11 + padding 8） | ≈ **200** → **超出约 76vp** |

卡片没有 `.clip(true)` → 溢出部分**画到相邻的「个人专注画像」卡上**，这就是"溢出/交叠"。

明细行同样：`Review.ets:1065-1081` 的 ``Text(`${item.subject}：${item.content}`)``
`content` 是任务标题（不定长）、列宽只剩约 98vp → 折成 3~4 行，卡片高度失控。

**整页没有任何截断保护**：`grep "maxLines|textOverflow|constraintSize|clip("` **零命中**。

### 修法

1. 两个标签改竖排（`Column`），或各自 `.layoutWeight(1).maxLines(1).textOverflow({overflow: TextOverflow.Ellipsis})`；
2. 明细标题加 `maxLines(1) + textOverflow`，右侧计数给固定宽（如 `.width(34)`）；
3. 卡片加 `.clip(true)` 兜底（防止将来再出现同类溢出）。

```ts
// pages/Review.ets:494-507
maxV = max(values)      // 只有 1 天非 0 → 也画满格；全 0 → maxV=1 → 贴底直线
```

1. 给 `summary` 加 `@Watch`，或在 `loadAll()` 末尾显式重画（重画前判 `lineCtx` 是否 ready）；
2. 纵轴改固定量程：`maxV = Math.max(60, 向上取整(max(values)))`，并在图上标纵轴刻度——避免单点满格。

## C1 · 首页今日任务排序

**结论：属实。** `Home.ets` 的 `refreshPlan()` 原来直接 `getCurrentPlan().slice()`，数组顺序就是规划返回的顺序，勾选完成后条目留在原位，已完成的反而可能一直占着列表顶部。

**改法**：渲染前做一次**稳定分桶** —— `未完成` 与 `已完成` 各自保持原有相对顺序，`未完成 ++ 已完成` 拼成新数组。不能就地 `sort()`（会打乱 AI/用户排好的先后），也不能复用同一个数组引用（ArkUI 同引用不重绘）。

顺带修掉一个更严重的问题：首页勾选任务原来调 `AppStore.togglePlanTask(id)` —— **只改内存、不落库、不重算聚合**，所以勾完任务完成率不变、重启状态还丢。已改为 `toggleTaskDone(id)`（落库 + `refreshAggregates()` + 广播刷新）。

**结论：属实，而且是 5 个独立缺陷叠在一起。**

用户场景：先聊出高数的计划 → 点「继续调整」→ 说"再加上英语" → 结果不对。逐条对上代码：

| # | 缺陷 | 证据 | 后果 |

## C3 · 结束专注后首页「今日数据」仍不更新（**修正 B1 的结论**）

B1 把断点定在"崩溃恢复到快照 → `startTime` 丢失 → 按日聚合恒 false"。这条修复是对的、也确实堵住了一类静默丢数据，但**它不是唯一断点** —— 用户第三次实测仍然复现，说明还有别的路径。这次逐条核到两处：

### 断点 A：派生值在 `@Watch` 回调里读镜像（最可能的主因）

`Home.refreshPlan()` 原来这样算完成率：

```
this.completionRate = this.todayTotal > 0 ? Math.round(this.todayDone / this.todayTotal * 100) : 0
```

`todayDone / todayTotal` 是 `@StorageProp` **镜像**，`refreshPlan` 又是被 `@Watch('dataVersion')` 触发的。而 `pushAggregates()` 是**连续写多个键**、最后才写 `DATA_VERSION`：

```
TODAY_FOCUS_SEC → TODAY_DONE_TASKS → TODAY_TOTAL_TASKS → FOCUS_RATE → … → DATA_VERSION
```

同一批属性更新里，`@Watch` 回调**不保证按写入顺序被处理**。一旦 `DATA_VERSION` 先被处理，回调就会拿着**还没同步的** `todayDone/todayTotal` 算出完成率；而 `DATA_VERSION` 之后不会再变，**这个错值就永久留在界面上**。表现正是"退出了，但数字没动"。

**改法（从根上消除顺序依赖）**：不再看镜像，**直接拉取 store 的权威聚合对象**。`refreshAggregates()` 里 `this.dashboard = d` 是一次整体赋值、发生在 `pushAggregates()` 之前，所以 `DATA_VERSION` 一变，`getDashboard()` 必定已是最新值，与更新顺序完全无关：

```
refreshPlan() {
  const d = AppStore.getInstance().getDashboard()
  this.dashTodayFocus = d.todayFocusSeconds; this.dashRate = d.focusRate
  this.dashDone = d.todayCompletedTasks; this.dashTotal = d.todayTotalTasks
  this.completionRate = …
}
```

`@StorageProp` 的 `TODAY_FOCUS_SEC / TODAY_DONE_TASKS / TODAY_TOTAL_TASKS / FOCUS_RATE` 四个镜像随之删除，`DATA_VERSION` 成为**唯一**的刷新触发点。（工作台的 `Dashboard.refresh()` 一直都是这么读的，所以它没出这个问题 —— 这也是"为什么工作台看着对、首页不对"的解释。）

### 断点 B：短会话结束后显示 "0min"，肉眼无法判断有没有刷新

`TimeUtils.formatHMin(45)` → `"0min"`，和没开始时**一模一样**。真机自测时一次会话往往只有几十秒，于是"看起来没更新"。已加 `focusSecondsText()`：不足 1 分钟按秒显示（`45秒`）。

### 断点 C：缺一个必经的兜底刷新点

`Home` 是 `Tabs` 的常驻子页，`router.back()` 回来既不重走 `aboutToAppear`，也不触发 `onChange`。原来的兜底只有"切 Tab 时刷新"，若用户直接在首页点「继续专注 → 结束」，回来时 Tab 没变，兜底不触发。已给根页 `Index` 加 `onPageShow()` → `refreshAggregates()`（**每个二级页返回都必经**，只做内存重算 + 广播，开销很小）。

> 三处一起改之后，无论走「直接结束 / 生成复盘 / 返回退出」哪条路，首页数据都不依赖"某个回调恰好触发"。

## C4 · 专注中切后台 → 识别为「手机使用」

**结论：属实，且是纯功能缺失。** 全项目没有任何 `onBackground` / `windowStageEvent` / `onPageHide` 的监听；切到别的应用后 `settleSegment` 仍在按墙钟累加，状态还是 `FOCUSED` —— 这几十秒会被算成**净专注**，报告里完全看不出"他其实在刷手机"。

### 判据设计（这里必须谨慎，否则会打掉核心场景）

**"进后台"本身不等于分心。** 本产品的前提就是"手机扣在桌上学习" —— 那时锁屏、App 也在后台。若把后台一律判成分心，等于把最核心的使用方式判成 100% 分心。

所以判据取**两个条件的交集**：

| 条件 | 依据 | 说明 |
|---|---|---|
| App 进入后台 | `UIAbility.onBackground()` | 不能用页面的 `onPageHide` —— 应用**内部**跳转（专注 → 答疑 / 休息）也会触发它 |
| 那一刻**屏幕是亮的** | `power.isActive()`（`@kit.BasicServicesKit`，since 9，**免权限**） | 亮屏 = 人在别的应用上（手机使用）；熄屏 = 手机被放下（照常算专注） |

再加一条时长门槛 `BG_PHONE_MIN_SEC = 30`，滤掉误触返回造成的秒级抖动。

### 为什么在"回前台"时才结算

后台定时器会被系统冻结，用 tick 累加会严重少算。所以：

- `onAppBackground()`：只 `settleSegment(now)`（把专注段结清到切走那一刻）+ 记下 `bgStartedAt / bgScreenOn / bgEligible`，**不下结论**；
- `onAppForeground()`：用真实时钟算出 `away` 秒，一次性归属：
  - 亮屏 + `away ≥ 30s` + 非暂停/休息/答疑 → 计入 `distractionSec`，写一条 `FocusSource.PHONE` 事件（`亮屏离开本应用 N 秒`），并走一次干预阶梯（把状态**临时**置为 `DISTRACTED` 交给 `InterventionEngine` 评估，评估完还原）；
  - 熄屏 / 离开过短 → 按当时的模式归入净专注；
  - 休息 / 暂停 / 答疑途中 → 归入对应累计值。

### 配套改动

- `FocusSource` 新增 `PHONE`（枚举 + 注释说明判据）；
- `EntryAbility` 新增 `onForeground()` / `onBackground()` 两个回调转发给控制器；
- `Metrics.distractionTriggers` 原来把**所有**非摄像头来源都写成"状态波动/视线离开屏幕"，会把手机使用伪装成视觉判定的结论 → 新增 `Metrics.sourceLabel(source)`，按来源输出 `切到其他应用（手机使用）` / `心率、HRV 波动` / `手动标记` / `AI 判断` / `视线离开屏幕`；
- `resetCounters / abort / finalize` 都调 `resetBackgroundProbe()`，避免脏时间戳打到下一段会话。

## C5 · 复盘洞察与建议算法（设计，待确认）

### 每日侧：现在为什么"哪一天都像同一句话"

`MockAIService.dayInsight()` 只有 3 档 `if`（`≥80` / `≥60` / 其它），输入只有 `focusRate + bestPeriod` —— 同一档里所有日子输出同一句。`daySuggestions()` 只有 3 条规则，其中"每 45 分钟休息""练习题分两批完成"**无条件出现**。

更关键的是：`Metrics.daySummary()` 明明拿到了 **30 秒粒度**的 `timeline`（`level 0-100` + `state`），却只拿它画色带，**一个结构指标都没算**。原料全在，洞察为零。

附带两个 bug：
- `daySummary().bestPeriod` 复用 `Metrics.goldenWindow()`，而后者**硬过滤"最近 14 天"**（`Metrics.ets:169`）→ 看 14 天以前任意一天，`bestPeriod` 恒为空 → `dayInsight` 回退成"当天状态最好的那一段"（句子里说"那一段"却不给时间）。
- 疲劳点判定过松：`MockAIService.ets:477-482` 取 `timeline` 里**第一个 `level < 45`** 的点，第 1 分钟一波动就报"疲劳"。

### 每日侧改法（用现成的 30s timeline 算"结构"，再和本人基线对比）

1. 新增 `Metrics.sessionStructure(s)`，从 `timeline` 算 6 个量：
   - `timeToFocus`：开始 → 首次进入 `FOCUSED` 的分钟数（**进入状态要多久**）
   - `longestRun`：最长连续 `FOCUSED` 段（分钟）
   - `bouts`：分心段（YELLOW+RED）次数
   - `recoveryMin`：每次分心回到 `FOCUSED` 的中位耗时（**被打断后多久能回来**，可干预、可展示）
   - `deepRatio`：`level ≥ 80` 的采样点占比
   - `tailDrop`：后 1/3 时段平均 `level` − 前 1/3 平均 `level` → 真正的疲劳拐点（替代"首个 level<45"）
2. 新增 `Metrics.baseline(sessions, excludeId)`：本人**近 7 天**同口径指标的中位数，作为对比基准。
3. 洞察 = **"这次 vs 你的常态"的差值**，每条自带数字。例如：
   - 「今天 45 分钟里进入状态用了 6 分钟，你平时是 2 分钟」
   - 「最长一段连续专注 18 分钟，比你这周的中位数短 9 分钟」
   - 「被打断 3 次，平均 4 分钟才回到专注」
4. 建议从洞察**派生**（`suggestionFor(key, value, baseline)`）：没有对应洞察就不出这条建议，去掉所有"无条件追加"的模板；一天最多 3 条。
5. 修掉 `goldenWindow` 的 14 天硬过滤：先看当天够不够样本，不够再退回近 14 天，并在文案里写明用的是哪种口径。

### 长期侧：现在为什么"几乎永远同一句"

`Metrics.habitInsights()` 的 6 个具体问题（全部有证据）：

| # | 问题 | 证据 |
|---|---|---|
| 1 | 分桶太粗：**2 小时一桶**，全天只有 12 档，"08:00–10:00"必然反复出现 | `Metrics.ets:445-462`、`bucketWindow()` |
| 2 | **高峰/低谷按"总学习时长"选，而不是专注率** → "学得久"被当成"效率高"；算出来的 `bucketRate` 只用于展示 | `Metrics.ets:468-477` |
| 3 | 初值 `peak = low = used[0]` + 严格 `>`/`<`，多个桶时长相等时 **bestWindow === lowWindow** → 建议句自相矛盾 | `Metrics.ets:468-477`、`advice` 在 `:494-501` |
| 4 | 门槛过低：只挡 `used.length === 0 / 1`，**2 个时段（可能只 2 次会话）就敢下"高峰 + 低谷"结论**；`goldenWindow` 连门槛都没有 | `Metrics.ets:464`、`:481`、`:179-193` |
| 5 | `loadAll` 传的是**全量 sessions、不限窗口**，一旦成型几乎不再变化 | `Review.ets:125` |
| 6 | 五维是"全历史平均"（`Metrics.fiveDim`），没有任何趋势；`longTermAnalysis` 只要 `sampleCount ≥ 3` 句式就固定 | `Metrics.ets:214-243`、`MockAIService.ets:863-901` |

### 长期侧改法

1. **1 小时桶（24 档）+ 样本门槛**：每档至少 **2 次会话**且累计总学习 ≥ 20 分钟才有资格参与评比；不够就明说"数据还不够，暂不判断低谷"。
2. **选峰/选谷改为专注率优先**：高峰 = 专注率最高且总学习过门槛；低谷 = 专注率最低。且要求 `bestRate − lowRate ≥ 8` 个百分点才说"有落差"，否则输出"各时段差别不大"。
3. **限定窗口为近 30 天**并在文案里写明 —— 与 `last30DaysSummary` 的口径对齐（现在是"全量 vs 近 30 天"两个口径混用）。
4. **加趋势与规律性**：近 7 天 vs 前 7 天（复用 `trendHeadline`，加 ≥10% 的显著性门槛）、连续学习天数、每周固定时段命中率。
5. `longTermAnalysis` 改为"**先给 1 个最显著的差异 + 1 条可执行建议**"，每条必须带数字和对比基准。
6. 落地位置：新增 `Metrics.insight*` 系列**纯函数**（沿用"指标只在 Metrics 算"的既有硬规则），页面只渲染；`MockAIService` 只保留兜底措辞。

> 补充：网关侧**目前完全没有 review / insight 场景** —— `GatewayAIService` 对 `review` 直接 `fail('review','not_implemented')`，`Prompts` 里也没有复盘 prompt，所以每日/长期洞察现在 **100% 是本地模板**。建议保持"本地算结构 + 规则生成"（可解释、可复现、不依赖网络），大模型只用于润色措辞。

## C6 · 工作台「任务进度」+ 目标 / 长期计划能否合并（设计，待确认）

### 先纠正一个前提：用户记忆里的引导流程与代码不符

- `Login.ets` 只收账号密码（`45-73`），**不收目标/时间/任务**；
- `GoalSetup.ets` 只收 ①目标类型（5 个候选）②目标日期（`DatePicker`），`goal.subjects = old.subjects`（`:108`）只是**把旧值原样继承**，**引导页一个任务都不创建**；
- **科目**全项目只有一个录入点：`LongTermPlan.ets:199`。

所以"引导登录时选目标 + 时间 + 任务（科目），然后按科目分类"这件事，在当前代码里并没有实现 —— 这是要说明的，不能按记忆去改。

### 再核对"进度直接弄了 100%"

**代码里没有任何地方把进度写死成 100。** `Task.done`（`Task.ets:12`）与 `PlanTask.done`（`StudyPlan.ets:16`）默认都是 `false`，`PlanTask.create` 恒为未完成；`Dashboard` 的进度是 `allDone / allTotal`（`Dashboard.ets:146-151`），分母 = `currentPlan` + `tasks` 按 id 去重后的条数。可能的三种来源：

1. 计划里只有 1 个任务且被勾上 → `1 / 1 = 100%`；
2. 把「本次专注得分」当成了任务进度 —— `StudyReport.ets:113-118` 的得分 = `100 − 走神占比`，没有分心就是 100；
3. 「科目进度」在某个科目只有 1 个任务且被勾上时，同样显示 100%（`AppStore.computeSubjectProgress()`）。

**但真正的问题是"进度"的语义没定义**：分子只由"用户手动打钩"驱动，`Task.actualDuration`（实际投入秒数，`finalize()` 已经在反算写回）**完全没参与**。所以它现在是"勾选完成率"，不是用户心里的"学习进度" —— 这解释了为什么用户觉得"这个进度没有依据"。

### 两个体系现在的真实关系

| 体系 | 字段 | 谁在写 | 谁在读 |
|---|---|---|---|
| `LearningGoal` | `examType` / `targetDate` / `subjects` / `title`(标语) | `GoalSetup`（仅 examType+targetDate）、`Login`、`LongTermPlan` | 首页/工作台倒计时与标语；`TaskPlanning.buildPlanningContext`；`Review` 目标行；`Metrics` 无 |
| `StudyPlan` | `title` / `examType` / `totalEstimatedMinutes` / `tasks` | **只有** `LongTermPlan.save()` | **只有** `TaskPlanning` 进 prompt；`Review` 显示一行标题 |

- **重叠**：`examType` 两边都有，`LongTermPlan.ets:124` 还把 goal 的 exam 复刻进 plan → 双写副本；`title` 同名异义（goal 里是**标语**，plan 里是**计划名**）。
- **死数据**：`StudyPlan.tasks` 从未被赋值、也无人读取；`LongTermPlan.save()` 每次 `StudyPlan.create()` 生成新 id → 表会累积多条记录（`loadStudyPlan` 只取一条）。

**结论：两者其实已经"半合并"了**（同一个页面、同一颗保存按钮，一次写两个模型），只是**数据层仍是两张表**，且语义已经漂移。所以问题不是"要不要合并"，而是"**收敛到哪个实体**"。

### 合并方案（推荐 A）

- **A · 收敛到单一 Goal 实体（推荐）**：把 `totalEstimatedMinutes` / 计划名并入 `LearningGoal`，删掉 `StudyPlan` 与 `study_plan` 表；`subjects` 保持"科目"的唯一来源；`LongTermPlan` 仍是唯一入口。
  - 迁移：`loadGoal()` 时若 `goal.totalEstimatedMinutes === 0`，尝试读一次 `study_plan` 回填，之后不再读该表（**一次性、幂等、可回滚**）。
  - 收益：倒计时、规划背景、长期进度参照读同一个对象；`examType` 不再双写；`GoalSetup` 与 `LongTermPlan` 的字段不再"一半在这、一半在那"。
- **B · 反向合并**（把目标塞进 `StudyPlan`、删 `LearningGoal`）：**不推荐** —— `LearningGoal` 被首页 / 工作台 / AI 规划 / 复盘 4 处读取，改动面远大于 A。
- **C · 只改标签不合并**：把「长期计划」降级为"目标"下的一个备注字段。成本最低，但"这一段时间要做成什么"仍然没有独立的进度参照 —— 等于没解决用户最初的诉求。

### 无论选哪个，都要先把「进度」的语义定清楚

1. **分母口径统一**：只算**当前计划里的任务**（用户说"进度"时想的就是这份计划），不把全部历史任务算进去 —— 现在 `allDone/allTotal` 含全部历史任务，越用越接近 0%，反而更没依据。
2. **分子升级为双口径**：既显示"勾选完成 X / Y"，也用 `actualDuration` 显示"计划时长已投入 Z / 总计划 W 分钟"。**后者才是用户要的进度，而且不需要用户手动打钩**（`FocusController.finalize()` 已经在按任务反算实际投入）。
3. **标签改名**：「总体进度」→「今日计划进度」，卡片上写明口径（"按勾选完成"或"按投入时长"），避免再被当成"学习进度"。
4. **科目进度**的分母同样只取当前计划；`subject` 为空时归入"未分类"一行，不要因为空科目多出一行。
