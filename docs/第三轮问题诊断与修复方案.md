### 1.3 为什么会「交叠」而不是「被裁掉」

主体 `Column` 有 `.layoutWeight(1)`，**但没有 `Scroll`**。ArkUI 的 flex 在空间不足时的行为是：子组件按自身尺寸绘制，不裁剪、不滚动 → 超出的部分直接**画到下方兄弟节点（底部按钮行）上面**，看起来就是交叠。

同时 `Stack({ alignContent: Alignment.BottomEnd })` 里的 **AI 悬浮球**（`L517-531`，`bottom: 90`）是脱离布局流的，会盖在中间的干预卡/任务卡上。

### 1.4 修法

**A. 删重复（立刻见效，0.1 天）**
1. 删掉 `L219-230` 的顶部任务块，任务信息只在勾选卡片里出现一次（或反过来：顶部保留任务名，卡片里只留勾选圈 + 计数）
2. 删掉「当前任务」标签
3. 把「感知依据」并进状态副标题一行，例如 `状态良好 · 视线正常 · 置信度 92%`

**B. 压缩高度（0.25 天）**，给一个可用预算：

| 区块 | 现在 | 改为 |
|---|---|---|
| 摄像头预览 | 150 + 20 间距 | **96 + 16**（并改名为"感知画面"，见问题 6），或**默认收起**，点击展开 |
| 计时器字号 | 68 | 56（间距 40 → 24） |
| 呼吸灯 | 150 + 48 间距 | 110 + 24 |
| 状态标题 + 副标题 + 依据 | 24+17+6+13+6+12 | 合并成两行：`20 + 6 + 14` |

改后基础占用 ≈ 39 + 480 + 78 ≈ **597vp**，留出 120–160vp 给条件卡片。

**C. 加 Scroll（0.25 天，必做兜底）**
```ts
// 主体改为：
Scroll() {
  Column() { /* 任务 / 计时 / 状态 / 卡片 */ }

.layoutWeight(1)
.scrollBar(BarState.Off)
```
⚠️ 注意：**计时器和呼吸灯不要放进 Scroll**（滚动时会把核心视觉滚走）。建议只把「状态区 + 各类卡片区」放进 Scroll，计时器固定在中间。

**D. 把 AI 悬浮球从 Stack 里搬进底部按钮行**（0.1 天）
现在的 `Stack(BottomEnd)` + `bottom: 90` 一定会压住内容。改成底部 3 按钮 + 1 个 AI 按钮的 4 等分横排，或用 `Flex` 让 AI 按钮占据独立一列。

**E. 暂停时清掉干预提示**
```ts

  this.lastDecision = null   // 或在 pushLive 里带一个 interventionActive 标记
}
```
或在前端：`if (this.interventionLevel.length > 0 && this.focusState !== 'PAUSED')`。

## 问题 2 · 问答界面布局

### 2.1 必现的溢出：`width('100%')` + 左右 margin

```ts
// pages/AIChat.ets:170-180
Button('← 回到专注（继续计时）')
  .width('100%')
  .height(44)
  .margin({ left: 20, right: 20, bottom: 8 })   // ← 致命组合
```

宽度 = 100% + 40vp → **按钮右侧被裁掉 40vp**，或者被父容器压缩到换行/错位。ArkUI 里 `width('100%')` 与水平 `margin` 是叠加的，不会自动扣减。

对照写法：下面的输入 `Row` 用的是 `.padding({ left: 16, right: 16 })`（`L208`），这是正确做法。所以你现在页面里**按钮左缩进 20、输入框左缩进 16，左右也不对齐**。

**修法（二选一）**
```ts
// 方案 1：包一层带 padding 的容器（推荐）
Row() {
  Button('← 回到专注（继续计时）').width('100%').height(44) /* ... */
}
.width('100%')
.padding({ left: 20, right: 20, bottom: 8 })

// 方案 2：去掉 width('100%')，改用 layoutWeight
```

### 2.2 顶栏会被撑高

```ts
private sceneLine(): string {
  return `本次专注 ${...} · 答疑 ${...} · 结束后自动回到专注${name}`
}
```

实测文本长度 ≈ 40–48 个字符（含任务名）。它放在一个 `layoutWeight(1)` 的 `Column` 里、右侧还有 `AITag()`，**没有 `maxLines`** → 会折成 2–3 行，把顶栏从 39vp 撑到 70vp+，进一步压缩消息区。

**修法**：`sceneLine()` 拆成两行短语，或 `.maxLines(1).textOverflow({ overflow: TextOverflow.Ellipsis })`，任务名过长时截断。

建议改成两行结构：

```
正在答疑
本次专注 42:36 · 答疑 03:21 · 结束后自动回到专注
```

第二行 `.maxLines(1)`，任务名放到第三行小字或直接不显示。

### 2.3 `AIFirstDisclaimer()` 挂错了父容器

```ts
// pages/AIChat.ets:128-210
Column() {
  Row() { ... }            // 顶栏
  Scroll() { ... }         // 消息区
  Button(...)              // 返回按钮
  Row() { ... }            // 输入栏
  AIFirstDisclaimer()      // ← 直接作为 Column 的 flex 子节点
}
```

`AIFirstDisclaimer` 未展示时渲染的是一个 `height('100%')` 的全屏 `Column`（`components/AIFirstDisclaimer.ets`）。虽然它内部用了 `.position()`，但**外层那个 `Column` 仍然作为 flex 子节点参与父级布局计算**，会把同级的 `Scroll`（`layoutWeight(1)`）压到很矮甚至 0。

同样的问题存在于 `AICompanion.ets:160` 和 `TaskPlanning.ets`。

**修法**：把它移出内容树，放到页面根 `Stack` 的最后一个子节点（和 `Index.ets` 的恢复弹窗一个写法）。或者直接把它改成用 `@Builder` + `.position()` 的自定义弹层，保证根节点不参与布局。

### 2.4 建议的问答页结构

```
Stack
├── Column
│    ├── 顶栏（两行 + AITag，第二行 maxLines 1）
│    ├── Scroll (layoutWeight 1)   ← 消息气泡
│    ├── 返回行（外层 Row 加 padding）
│    └── 输入行（padding 16）
└── AIFirstDisclaimer()
```

## 问题 4 · 手动点击完成任务

### 4.1 问题定位

```ts
// pages/Focus.ets:351-359
Checkbox()
  .select(this.planDone >= this.planTotal)   // ← 只在"全部完成"时才勾上
  .selectedColor(Colors.PRIMARY)
  .width(22)
  .height(22)
  .enabled(this.planDone < this.planTotal)
  .onChange(() => { this.completeTask() })
```

用户操作序列（4 个任务）：

| 步骤 | planDone/planTotal | Checkbox 视觉 | 任务名 |
|---|---|---|---|
| 初始 | 0 / 4 | 空 | 任务 1 |
| 点一下 | 1 / 4 | **空（自己弹回去了）** | 任务 2 |
| 再点 | 2 / 4 | **空** | 任务 3 |
| 点第 4 次 | 4 / 4 | **实心** | 今日任务已全部完成 |

→ **前 3 次点击在视觉上"什么都没发生"**，用户会以为按钮坏了。这就是你说的「手动点击完成任务」的问题。

根因：`Checkbox` 的 `select` 语义是「**这个任务**完成了吗」，但这里绑定的是「**所有任务**都完成了吗」。而勾选后任务会立刻切到下一个，所以 checkbox 天然无法表达"我刚完成了上一个"。

另外：`.enabled(this.planDone < this.planTotal)` 在全部完成后会**禁用复选框**，此时卡片仍显示——用户看到的是一个灰色的、勾着的、点不动的框，也不知道该干什么。

### 4.2 修法（推荐方案 A）

**A. 改成按钮式「完成当前任务」（推荐，0.25 天）**

```ts
if (this.hasPlan) {
  Column() {
    Row() {
      Column() {
        Text(this.taskSubject).fontSize(12).fontColor(Colors.TEXT_SECONDARY)
        Text(this.taskTitle).fontSize(15).fontWeight(FontWeight.Medium)
          .fontColor(Colors.TEXT_PRIMARY).margin({ top: 2 })
      }
      .alignItems(HorizontalAlign.Start)
      .layoutWeight(1)

      Text(`${this.planDone}/${this.planTotal}`)
        .fontSize(13).fontColor(Colors.TEXT_TERTIARY)
    }
    .width('100%')

    if (this.planDone < this.planTotal) {
      Button('✓ 完成当前任务')          // 明确的动作按钮，不是含糊的勾选框
        .width('100%')
        .height(40)
        .fontSize(14)
        .fontColor(Color.White)
        .backgroundColor(Colors.PRIMARY)
        .borderRadius(20)
        .margin({ top: 12 })
        .onClick(() => { this.completeTask() })
    } else {
      Text('今天的任务都完成了，可以结束本次专注')
        .fontSize(12).fontColor(Colors.TEXT_TERTIARY).margin({ top: 10 })
    }
  }
  /* 卡片样式 */
}
```

**B. 如果一定要保留勾选框**：加一个本地完成反馈，用 `@State justCompleted: boolean` 在 800ms 内把框保持为勾选态再切换任务：
```ts
private completeTask(): void {
  if (!FocusController.getInstance().completeCurrentTask()) return
  this.justCompleted = true
  setTimeout(() => { this.justCompleted = false; this.refreshTask() }, 800)
  AppStore.getInstance().setCurrentPlan(FocusController.getInstance().getTasks())
  AppStore.getInstance().syncPlan()
}
// Checkbox().select(this.justCompleted)
```

**C. 顺带补上「任务列表」（0.5 天，强烈建议）**
专注页现在**看不到完整的任务列表**，用户不知道还剩几个、都是什么。建议在任务卡片下方加一个可展开的列表（点击展开 4–5 条），每条可点选切换当前任务。`FocusController.switchToTask(id)` **已经写好了**，只差 UI。

**D. 注意 Home 的勾选是正常的**
`Home.ets:287-297` 用 `TaskCard({ done: task.done, onToggle: ... })`，`select` 绑的是该任务自己的 `done` → 行为正确。**但专注中看不到 Home**，所以专注页必须有入口。

## 问题 5 · 复盘的总学习时长 / 净专注时长 / 曲线算法

### 5.1 计时链路（`FocusController`）

```ts
private recomputeTick(): void {
  const dtMs = Math.min(now - this.lastTickAt, FocusTuning.MAX_TICK_DELTA_MS)  // 5s 封顶，防后台差值爆炸
  this.totalSec += dtMs / 1000          // 墙钟：含休息 / 暂停 / 答疑
  if (paused)  { this.pausedAccum += dt; return }        // 只累加暂停
  if (resting) { this.breakSec    += dt; return }        // 只累加休息
  if (qaMode)  { this.qaSec       += dt }                // 答疑：计入总学习，不计净专注
  else if (state === FOCUSED) { this.focusSec += dt }    // 净专注
  else { this.distractionSec += dt }                     // 黄 + 红
  this.sampleAccumMs += dtMs
  if (this.sampleAccumMs >= FocusTuning.TIMELINE_SAMPLE_MS) {  // 30_000
    this.sampleAccumMs = 0
    this.sampleTimeline()
  }
}
```

`finalize()` 把浮点秒取整写回 `session`：

| 字段 | 含义 |
|---|---|
| `totalDuration` | 墙钟（秒） |
| `focusDuration` | 净专注 = GREEN 累计 |
| `distractionDuration` | 分心 = YELLOW + RED |
| `qaDuration` | 答疑 |
| `breakDuration` | 休息 |
| `pausedDuration` | 暂停 |

### 5.2 三个指标的口径（`Metrics`）

| 指标 | 公式 | 代码 |
|---|---|---|
| 墙钟 | `totalDuration` | `Metrics:71` |
| **总学习** | `totalDuration − breakDuration − pausedDuration` | `Metrics:86` |
| **净专注** | `focusDuration` | `Metrics:91` |
| **净专注率** | `focusDuration / (totalDuration − break − pause)` | `Metrics:106` |
| 分心率 | `distractionDuration / 总学习` | `Metrics:117` |
| 完成率 | `completedTaskIds / taskIds`（空任务集返回 0） | `Metrics:126` |

### 5.3 ⚠️ 同页口径矛盾（必改）

`pages/StudyReport.ets:35`：

```ts
this.totalStr = TimeUtils.formatDuration(session.totalDuration)   // ← 墙钟，含休息+暂停
```

而同一页的「净专注率」来自 `report.focusRate` = `Metrics.focusRatePercent()` = `focus / (total − break − pause)`。

**所以「总学习时长」和「净专注率」的分母不是同一个东西。** 举例：

| 真实情况 | 页面显示 |
|---|---|
| 墙钟 60min，休息 10min，暂停 10min，净专注 40min | 总学习时长 **60min** / 净专注时长 40min / 净专注率 **100%** |

用户一算：40 / 60 = 67%，但页面写 100% → **看起来像算了假数据**。

更糟的是同一页的 AI 洞察用的是**正确口径**：
```ts
// MockAIService.produceReview
const studyMin = Math.round(Metrics.totalStudySec(s) / 60)   // 40 分钟
insight = `本次一共学习了 ${studyMin} 分钟…`
```
→ 卡片写「总学习时长 60min」，AI 却说「一共学习了 40 分钟」。**同一屏自相矛盾。**

**修法**
```ts
// pages/StudyReport.ets
this.totalStr = TimeUtils.formatDuration(Metrics.totalStudySec(session))   // 用总学习口径
this.breakStr = TimeUtils.formatDuration(session.breakDuration)
this.pauseStr = TimeUtils.formatDuration(session.pausedDuration)
this.qaStr    = TimeUtils.formatDuration(session.qaDuration)
```
并把「专注数据总览」改成自解释的两列：

| 列 | 值 |
|---|---|
| 总学习时长 | 40min（= 墙钟 60min − 休息 10min − 暂停 10min） |
| 净专注时长 | 40min |
| 净专注率 | 100% |
| 分心 / 答疑 / 休息 / 暂停 | 分开列，让用户能验算 |

### 5.4 曲线算法

**采样（两个触发点）**

1. 时间驱动：`sampleAccumMs` 累计到 `TIMELINE_SAMPLE_MS = 30_000` 采一点
2. **状态驱动**：`transitionTo()` 里也会调一次 `sampleTimeline()`（**不重置 `sampleAccumMs`**）

→ 采样点**在时间上不是等距的**。

**点内容**
```ts
private sampleTimeline(): void {
  const p = new FocusTimelinePoint()
  p.minute = Math.floor(this.totalSec / 60)      // 会话内相对分钟
  p.level  = this.levelForState(this.state)      // 92 / 62 / 30 三档
  p.state  = this.state
  this.timeline.push(p)
}
```

**绘制（`FocusChart.ets`）**
```ts
const stepX = (w - pad * 2) / Math.max(1, n - 1)
const x1 = pad + i * stepX                        // ← 按索引等距排布
```

**两个已知偏差**
1. **X 轴按索引等距，不按真实时间。** 采样间隔不均匀（状态切换会多采），所以曲线的横向比例失真。短会话下（只采了 2–3 点）会更明显。
2. **`p.minute` 是会话内相对分钟，但 `Metrics.clock()` 把它当"当天第几分钟"格式化。** 于是 `bestFocusPeriod` 会返回 `00:25 - 00:30` 这种值，而不是 `09:55 - 10:00`（应加上 `session.startTime` 的小时/分钟）。
   → 目前 `bestFocusPeriod` **没有任何页面渲染**（`grep pages/` 为 0 命中），所以还没暴露，但已经写进 DB 了，一旦加 UI 就会露出来。
   → 修法：`Metrics.bestFocusPeriod(s)` 里用 `s.startTime` 换算真实时钟，或干脆返回"第 N 分钟 - 第 M 分钟"的相对表述（更不易误解）。

**A 曲线的三档阶梯问题**
`level` 只有 92 / 62 / 30 三个值（上一轮为了去随机数改成确定性推导，这个方向是对的）。代价是曲线变成阶梯线，视觉上不像"专注度曲线"。
如果想让曲线更自然，建议**不要把随机数加回来**，而是用"状态 + 该状态内的相对位置"插值（例如 GREEN 段内 88→94 缓变），并在 UI 上标注"示意曲线，纵轴为状态等级"。**诚实比好看重要。**

### 5.5 `habitInsights` 仍是硬编码（上一轮遗留）

```ts
// Metrics.ets:408-410
lowWindow: '晚间 21 点后',        // 写死
lowNote: '容易分心',              // 写死
advice: '难题优先安排上午攻克，晚间以复习和轻量整理为主。'  // 写死
```
而且 `bestRate` 累加的是**全部会话**的平均净专注率，不是 `bestWindow` 时段内的。`Review` 页面「学习习惯洞察」区块直接展示了这三条 → 用户会看到与自己数据无关的建议。

**修法**：低谷时段 = 12 个 2h 桶里总学习时长最少且低于均值的桶；`bestRate` 只统计落进 `bestWindow` 的会话；建议由高峰/低谷对比生成。

## 执行进展（第六轮 · 专注感知重构：手表事件驱动 + 云端识别）

### 为什么推倒重来
前两版的"专注感知"都被否掉：①固定 160 秒脚本凭空产生绿/黄/红；②用**头姿/视线是否朝向屏幕**判分心——**构念不成立**，用户学习时在做题/看书，本来就不看手机。

### 文献调研结论（网络受限，只读到摘要/二手转述，可靠度按此打折）
- **站得住**：把"手机被使用"当分心事件记录（StudentLife, Wang et al., UbiComp 2014；Sapci 2021；Elhai 2021）；仅凭设备自身信号推断注意力状态（Pielot et al., CHI 2014, 70.6%/81.2%）。
- **站不住**：头姿判专注；**短窗口 RMSSD 做个体在线判断**（Bourdillon 2017 需 ≥2min 且仰卧；Charles & Nixon 2019 综述 58 篇"无单一指标能清晰判别心理负荷"；Mund & Schulte 未能复现）；PERCLOS 在学习场景未验证（出处 Dinges/Mallis/Maislin/Powell 1998, NHTSA DOT HS 808 762，**不是常见误引的 "Dinges & Grace"**）。
- **搜不到**：手机 pickup-detection 准确率研究；纸质学习场景的走神自动检测。

### 确定的架构（级联 + 事件驱动）
手表粗筛 → 可疑时触发摄像头抓 2–3 秒 / 5–8 帧 → 上传云端 → 云端**只输出可观察状态** → App 规则组合。端到端 3–8 秒，故**本地规则负责即时干预，云端只负责标注与归因**。
