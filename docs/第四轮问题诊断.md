## 问题 1 · 从规划页进入专注导致摄像头调用失败

### 1.2 为什么「从首页进没事、从规划页进就挂」

**根因：`.onAppear` 不保证 surface 已创建。**

`XComponent.onAppear` 是"组件挂载"回调，触发时 XComponent 的 Surface 可能还在创建中；此时 `XComponentController.getXComponentSurfaceId()` 返回**空字符串**。
我看过本机 SDK 的定义，`XComponentController` 提供的才是可靠入口：

```
C:\Program Files\Huawei\DevEco Studio\sdk\default\openharmony\ets\component\xcomponent.d.ts
  line 242  getXComponentSurfaceId(): string          // 随时可调，未创建时返回 ''
  line 382  onSurfaceCreated(surfaceId: string): void // ★ surface 创建完成，直接给出 surfaceId
  line 405  onSurfaceChanged(surfaceId, rect)
  line 426  onSurfaceDestroyed(surfaceId)
```

**两个入口的差别不是路由，而是「谁先跑赢这个竞态」：**

| 入口 | `camGranted` | `tryStartCamera` 里是否有 await 缓冲 | 结果 |
|---|---|---|---|
| **首页**（`Home.beginFocus` → 可能先弹权限框） | 首次为 `false` → 有 `await ensureCamera()` | **有**（几百 ms，surface 早已建好） | 大概率成功 |
| **首页**（已授权过，直接进） | `true` | 无 await | 临界 |
| **规划页**（`TaskPlanning.confirmStart`） | `true`（之前授权过） | **无** | 竞态失败概率最高 |
| **规划页**（`persistPlan()` 落库后立刻 pushUrl） | `true` | 无 | 主线程刚做完 RDB 写，surface 创建更晚，**最容易输** |

所以：

> 这不是"规划页少做了一个开关"，而是**一个一直存在的竞态**。
> 从首页进时，因为中间夹了一次系统权限框（`await`），侥幸躲过了；
> 从规划页进时，前面刚 `await persistPlan()` 落库、页面又是重页（长聊天列表），
> pushUrl 后 `onAppear` 更早触发，就输了。

### 1.3 致命的第二点：**没有任何重试路径**

```ts
// Focus.ets:120-143
onPageShow(): void {
  ...
  if (this.firstShow) {
    this.firstShow = false
    return                       // ★ 首次进入直接 return，不尝试开相机
  }
  if (this.camCount > 0) {
    this.tryStartCamera()        // 只有"从休息/答疑返回"才会走到这里
  }
}
```

- 首次进入：靠 `XComponent.onAppear` —— **一次机会，失败就永久失败**
- 用户唯一的补救是画面下面那行 11px「重试」链接（很小，且只在 `cameraError` 非空时出现）
- 一旦失败，整个会话里 `CameraService.running` 恒为 `false` → **这次专注的所有触发都抓不到帧**

### 1.4 先花 1 分钟确认是不是这个问题

**在专注页点一次「模拟状态」按钮，然后看 SimWorkbench 里「上次抓拍：」那一行：**

| 显示内容 | 结论 |
|---|---|
| `真实抓拍未取到帧（预览未运行，无法抓拍）` | ✅ **就是本问题**（预览没起来） |
| `真实抓拍未取到帧（上次抓拍尚未结束，本次跳过）` | 连点两次导致的重入保护，不是本问题 |
| `真实抓拍未取到帧（等待 photoAvailable 超时（3000ms））` | 是交接文档的**假设 A**（回调不触发） |
| `真实抓拍未取到帧（取 JPEG 分量失败 code=… format=…）` | 是交接文档的**假设 B**（不是 JPEG） |
| `真实抓拍失败：本机不支持「预览 + 拍照」同会话` | `NORMAL_PHOTO` 无 `photoProfiles`，走了退路 |

另外看预览框下方那行红字（`Focus.ets:454` 的 `cameraError`）：**如果显示「预览 surface 未就绪」，就百分百坐实。**

### 1.5 修复方案（4 处，堵掉竞态）

**① `tryStartCamera` 改成"等 surface 就绪"的带重试版本**（根治，零 API 类型风险）

```ts
// Focus.ets
/** 上一次成功拿到的 surfaceId，避免重复取 */
private surfaceId: string = ''

/**
 * 拉起前置预览。
 * 关键：XComponent.onAppear 触发时 Surface 往往还没创建，getXComponentSurfaceId() 返回空，
 * 此处按 120ms 间隔重试若干次，等 surface 真正就绪再开相机。
 */
private async tryStartCamera(retry: number = 0): Promise<void> {
  const ctx = getContext(this) as common.UIAbilityContext

  // 先要权限（这一步本身也是给 surface 留时间）
  if (!this.camGranted) {
    this.camGranted = await PermissionService.getInstance().ensureCamera(ctx)
  }
  if (!this.camGranted) {
    this.cameraError = '未授予相机权限'
    return
  }

  let sid = this.surfaceId
  if (sid.length === 0) {
    sid = this.camController.getXComponentSurfaceId()
  }
  if (sid.length === 0) {
    // surface 还没建好：退避重试，最多 10 次（约 1.2s）
    if (retry < 10) {
      setTimeout(() => { this.tryStartCamera(retry + 1) }, 120)
    } else {
      this.cameraError = '预览画面未就绪，可点「重试」'
    }
    return
  }
  this.surfaceId = sid

  // 已成功运行就不用重复开（避免把正在跑的会话拆掉）
  if (CameraService.getInstance().isRunning()) {
    this.cameraError = ''
    return
  }
  const ok = await CameraService.getInstance().startPreview(ctx, sid)
  this.cameraError = ok ? '' : CameraService.getInstance().getLastError()
}
```

**② 首选方案（更干净）：改用 `onSurfaceCreated`**

`XComponentController` 明确提供 `onSurfaceCreated(surfaceId)`，这是"surface 创建完成"的权威回调。可以两套并存——`onSurfaceCreated` 一到就开相机，`onAppear` 那条重试链作为兜底：

```ts
aboutToAppear(): void {
  // ...
  this.camController.onSurfaceCreated = (surfaceId: string) => {
    this.surfaceId = surfaceId
    this.tryStartCamera()
  }
  this.camController.onSurfaceDestroyed = () => {
    this.surfaceId = ''
    CameraService.getInstance().stopPreview()
  }
}
```
> ⚠️ 这个赋值写法请先在 DevEco 里编译确认（`onSurfaceCreated` 在 d.ts 里是方法签名，赋值形式是否被 ArkTS 接受取决于 API 版本）。**如果不能编译，就用方案 ① 的重试链，效果等价。**

**③ `onPageShow` 的首次分支不要直接 return**

```ts
onPageShow(): void {
  // ... FOCUS_END_REQUEST 处理不变 ...
  if (this.firstShow) {
    this.firstShow = false
    // 首次进入也要兜一次：onAppear 可能早于 surface 创建，这条路作为第二道保险
    if (this.camCount > 0) {
      this.tryStartCamera()
    }
    return
  }
  if (this.camCount > 0) {
    this.tryStartCamera()
  }
}
```

**④ `captureBurst()` 的失败原因要能区分「预览没起来」和「预览起来但抓不到帧」**

现在这两种都归到一句「真实抓拍未取到帧」，导致排查时分不清。建议：

```ts
async captureBurst(): Promise<ArrayBuffer[]> {
  if (!this.running || this.photo === null) {
    this.lastError = this.running
      ? '预览会话里没有拍照输出（本机不支持预览+拍照同会话）'
      : '预览未启动'                       // ← 与"抓不到帧"分开，一眼可辨
    ...
  }
  ...
}
```

### 1.6 顺带一个隐患：`stopPreview()` 没有 await

```ts
// Focus.ets:113-117
aboutToDisappear(): void {
  FocusController.getInstance().setOnIntervention(null)
  CameraService.getInstance().stopPreview()      // ← async 但没有 await / void
}
```

`stopPreview()` 内部先 `await session.stop()` 再 `await session.release()`，**最后才把 `running` 置 false**。而 `startPreview()` 第一行是：

```ts
if (this.running) {
  return true          // ← 返回 true，但 session / photo 已被上一页释放成 null
}
```

→ 如果用户在上一页刚销毁、新 Focus 页立刻创建，`startPreview` 可能直接返回 `true`，而 `photo` 是 `null` → 后面 `captureBurst` 报「预览会话里没有拍照输出」。虽然概率低，但和上面是同一类问题。

**修法**：`startPreview` 的早退条件加严——
```ts
if (this.running && this.session !== null && this.photo !== null) {
  return true
}
```
并在 `aboutToDisappear` 里写成 `void CameraService.getInstance().stopPreview()` 明确表示"不等待"。

### 1.7 一个给演示的保护（强烈建议）

如果演示现场真的抓不到帧，**不要让复盘显示"抓拍未取到帧（预览未运行）"这种技术文案**。建议在 `Focus` 页预览框下面加一行明确的状态：

```
● 感知就绪 · 触发时会抓拍        （running === true）
● 感知未就绪 · 点此重试           （running === false，可点）
```

这样演示时一眼能判断"现在能不能抓拍"，而不是等点完按钮去复盘里找原因。

## 问题 3 · 个人画像雷达图的五维算法

先说结论：**你的直觉是对的。这不只是"某一维算得不准"，而是五维里有两维在数学上重复、另有一维是它们的线性组合——实际只有 3 个独立维度。**

### 3.1 现在的算法（`Metrics.fiveDim()`，`Metrics.ets:382-411`）

```ts
const finished   = sessions.filter(s => totalStudySec(s) > 0)
const rates      = finished.map(s => netFocusRate(s) * 100)        // 净专注率
const avgRate    = mean(rates)
const sigma      = stddev(rates) / 100

const taskSessions = finished.filter(s => s.taskIds.length > 0)     // 有任务清单的
const avgComp      = mean(taskSessions.map(s => completionRate(s)))

const perceptionSessions = finished.filter(s => perceptionMode === PERCEPTION_FULL)
const avgDistr           = mean(perceptionSessions.map(s => distractionRate(s)))

efficiency      = 0.6 * avgRate + 0.4 * avgComp
concentration   = avgRate
stability       = sigma > 0.3 ? 0 : 100 * (1 - clamp(sigma / 0.4, 0, 1))
execution       = avgComp
antiDistraction = 100 * (1 - clamp(avgDistr, 0, 1))
```

### 3.2 缺陷一：五维实际只有 3 个独立维度 ⭐

**证明 —— 「抗干扰」与「专注度」是同一个东西：**

在 `recomputeTick()` 里，非暂停/非休息时每一秒只会计入三者之一：

```
focusSec + distractionSec + qaSec = totalStudySec        （精确成立）
→ netFocusRate + distractionRate + qaRate = 1            （每一场会话都成立）
```

对会话集合取平均：
```
mean(netFocusRate) + mean(distractionRate) + mean(qaRate) = 1
```

代入定义：
```
concentration   = 100 × mean(netFocusRate)
antiDistraction = 100 × (1 − mean(distractionRate))
                = 100 × (mean(netFocusRate) + mean(qaRate))
                = concentration + 100 × mean(qaRate)
```

> **也就是说：`抗干扰 = 专注度 + 100 × 平均答疑时间占比`。**
> 答疑通常只占 0~5%，所以这两个数**几乎恒等**——雷达图上这两个顶点永远几乎重合。

**再看「效率」：**
```
efficiency = 0.6 × avgRate + 0.4 × avgComp
           = 0.6 × concentration + 0.4 × execution      （取整前精确成立）
```

**结论：**

| 维度 | 性质 |
|---|---|
| 专注度 | **独立** |
| 执行力 | **独立** |
| 稳定性 | **独立** |
| 效率 | = 0.6·专注度 + 0.4·执行力（纯派生） |
| 抗干扰 | ≈ 专注度（差一个常数） |

**五维实际只承载 3 维信息。** 用户拉的永远是一个"三角形被投影成五边形"的形状，两三个顶点永远一起动。这正是你觉得"有点问题"但说不清哪不对的地方。

**还有一个更细节的坑**：`concentration` 用**全部**会话算，`antiDistraction` 只用**感知开启**的会话算。当前两者的差异**不是"衡量了不同的东西"，而是"样本集不同"**——雷达图上这两维的差值是采样偏差，不是真实差异。这比单纯重复更糟。

### 3.3 缺陷二：没有任务清单时「效率」被无故拉低 ⭐

```ts
const avgComp = comps.length > 0 ? mean(comps) : 0      // 没有任务时 = 0
efficiency = Math.round(0.6 * avgRate + 0.4 * avgComp)  // → 0.6 × avgRate
```

而页面标记缺失维度时：

```ts
// FocusProfile.ets:36
this.dimMissing = [false, false, false, p.taskCount === 0, p.perceptionCount === 0]
//                  ↑效率永远 false（不标记缺失）
```

→ 一个只用「自由专注」的用户（不规划任务），如果净专注率是 85，雷达图会显示：
- 专注度 **85**
- 效率 **51** ← 而实际只是 `0.6 × 85`，**不是真的效率低**
- 执行力 → 标为「—」（正确）

**用户会看到"效率"莫名其妙比"专注度"低 34 分，且没有任何说明。** 这是雷达图上最容易被一眼看出的异常。

### 3.4 缺陷三：稳定性会直接归零，且 n=3 时标准差无意义

```ts
stability = sigma > 0.3 ? 0 : 100 * (1 - clamp(sigma / 0.4, 0, 1))
```
`sigma` 是**净专注率（0–1 尺度）的标准差**。

- 门槛：样本门禁是 `sampleCount >= 3`。**用 3 个样本算标准差，本身就不稳定**：加一次会话，`stability` 可能从 80 直接掉到 0。
- 断崖：`sigma > 0.3 → 直接 0`。两个会话分别是 0.55 和 0.95，`sigma ≈ 0.2`；再加一个 0.3 的会话，`sigma ≈ 0.27`；再多一个 0.2 → `sigma ≈ 0.32` → **稳定性从 33 直接变 0**，用户看到的是"完全不稳定"，而事实上只是有几场专注度低。
- 口径窄：只用"净专注率"的波动代表"稳定性"，**不看专注时长的波动、也不看分心次数的波动**。而 PRD 里"稳定性"的业务含义是"表现波动程度"。

### 3.5 缺陷四：各维度样本量不同，却同等展示

`execution` 可能只由 1 场有任务的会话算出（`taskCount = 1`），`antiDistraction` 可能只由 1 场开摄像头的会话算出，而 `concentration` 由全部 N 场算出。**但雷达图上五个顶点看起来同等可信。** 页面虽然加了 `coverageNote()` 说明"暂不可评"，但只在 `taskCount === 0` / `perceptionCount === 0` 时才提示；`taskCount = 1`（等于拿一次会话下结论）是**不提示的**。

### 3.6 缺陷五：「效率」的公式与业务含义不符

注释写的是「效率 = 单位时间产出」，但公式 `0.6×净专注率 + 0.4×完成率` 里**没有任何"产出/时间"的成分**——没有任务实际耗时、没有题量。它实际衡量的是"综合表现"。

**而真正的效率数据你已经有了**：`FocusController.ets:347` 已经在按任务归属曲线**分段反算实际投入**并写回 `Task.actualDuration`；`Metrics.planProgress` 里也在用 `actualMinutes`。用「实际投入 vs 预估时长」算效率，才符合"单位时间产出"的语义。

### 3.7 改法建议

**A. 让五维真正独立（0.5 天）**

| 维度 | 现状 | 建议公式 | 依据数据 |
|---|---|---|---|
| **效率** | `0.6×专注率 + 0.4×完成率` | `预估达成率 / 实际投入率`，即 `Σ(已完成任务预估分钟) / Σ(实际投入分钟)`，clamp 到 100。无任务时不评（标记缺失） | `Task.estimatedDuration` / `Task.actualDuration` |
| **专注度** | `平均净专注率` | 保持 | — |
| **稳定性** | `净专注率 σ`（会归零） | 改为**多信号合成**：净专注率 σ、单次时长变异系数、分心次数波动三者归一后取加权；并把断崖改成软着陆（如 `σ>0.35` 时下限 30 而非 0）；`sampleCount < 5` 时标记"样本不足"而不给数 | 会话序列 |
| **执行力** | `平均完成率` | 保持（口径正确），但样本 < 3 时标记"样本不足" | `completionRate` |
| **抗干扰** | ≈ 专注度 | **改口径**：用「分心事件后回到专注的比例」，即 `干预后恢复专注次数 / 干预总次数`，或 `100 − 单位时长分心次数归一` | `session.interventions`（已落库，含 `userFeedback` / `recoveredFocus`） + `distractionSec` |

> **关键**：`session.interventions` 里已经有 `InterventionEvent.userFeedback` 和 `recoveredFocus` 字段，`InterventionEngine.recordUserFeedback()` 也已接上 UI（Focus 页干预卡的三个按钮）。**"抗干扰"最贴切的定义就在这里，而且数据已经在采集。**

**B. 修掉「效率」被无故拉低（0.1 天）**
```ts
// FocusProfile.ets / Review.ets
this.dimMissing = [
  p.taskCount === 0,        // 效率：无任务清单 → 缺失（原来写死 false）
  false,
  p.sampleCount < 5,        // 稳定性：样本太少 → 缺失
  p.taskCount === 0,        // 执行力
  p.perceptionCount === 0   // 抗干扰
]
```
并在 `Metrics.fiveDim` 里对 `avgComp` 缺失的情况**返回缺失标记**而不是拿 0 参与加权：
```ts
// 建议 FiveDim 增加 efficiencyValid 之类的标志，或让 efficiency 在无任务时返回 -1 表示"不可评"
```

**C. 加一条"个人基线"参照（可选，0.5 天）**
`Metrics` 里已经有 `Baseline` 接口（近 7 天 / 近 30 天窗口 + 门槛 + 排除当天），但雷达图只画了绝对分。建议雷达图**外面叠一层"你的基线"虚线多边形**，让"这次比基线好还是差"一眼可见——这比五个绝对分数更有说服力，也更像"画像"。

**D. 页面上要说清楚（0.25 天）**
- 五个维度各配一句 **≤ 10 字**的口径说明（长按或点问号展开）
- 缺失维度继续用「—」（现在做对了），并补上 `taskCount` / `perceptionCount` 的具体样本数，如 `执行力（1 次样本，暂不可评）`
